# DealFlow360 — Phase 5 API Design
## Fulfillment + Multi-Warehouse Allocation (`plan.md` Hour 4.5–5.5)

Builds on Phase 1 (auth/RBAC/response envelope), Phase 2 (`categories`/`products`, admin-CRUD conventions), Phase 3 (`quotations`, `quotations.calc`), and Phase 4 (`approval` — a quotation now reaches `status='APPROVED'` either by auto-approval at submit or by the final approval action). Scope is strictly §5.1–5.4 of `plan.md`: Warehouse Setup, the Auto Allocation Engine, the Fulfillment read/override surface, and Backorders. Hybrid billing (Phase 6) and the customer portal (Phase 7) are **not** built here.

---

## 1. Assumptions carried into this phase

1. **Warehouse & stock configuration (`plan.md` §A4 / §5.1) belongs here, not Phase 2.** Phase 2 explicitly scoped itself to plan.md §2.1–2.5 (Product, Customer, Price Lists, Discount Governance, Approval Engine) and never touched `warehouses`/`warehouse_stock`. `plan.md`'s own phase breakdown puts "5.1 Warehouse Setup" inside Phase 5, and the Problem Statement's Admin responsibilities ("warehouses" in its backend-setup list) are honored by giving this CRUD to `ADMIN`, consistent with Phase 2's pattern for catalog/pricing config.
2. **Order creation is a gap in `plan.md`'s own API list, filled here as `POST /orders/from-quotation/:quotationId`.** `plan.md`'s "API Priority" section jumps straight to `GET/POST /api/orders/:id/...` for fulfillment without ever listing an endpoint that creates the `orders` row in the first place, yet the schema's 1:1 `orders.quotationId` unique index and `order_items` clearly need a writer. Per the Problem Statement's flow ("Once approved ... the system suggests a warehouse fulfillment split" and the Quick Test Flow's own ordering — approval, *then* warehouse split, *then* hybrid billing, *then* portal negotiation, *then* final customer confirmation) the order object is created right after approval, not deferred to customer confirmation. Phase 4's own forward-note already committed to triggering fulfillment "off `quotations.status = 'APPROVED'`... without modifying" Phase 3/4 — so this phase cannot hook into the `submit`/`approve` transactions directly. Instead it exposes an explicit, idempotent conversion endpoint that the frontend calls the moment it observes `quotation.status === 'APPROVED'` (e.g. on first opening the B6 Fulfillment screen, or immediately chained after the approve response). This is additive; Phase 3/4 files are untouched.
3. **Order creation auto-triggers the first allocation pass as a second, separate transaction, not folded into the same transaction as the order insert.** Keeping "create the order" and "compute an allocation" as two atomic units (rather than one giant transaction) means a transient allocation failure (e.g. zero stock anywhere) never prevents the order from existing — the client can always retry `POST /orders/:id/allocate` independently. This matches Rule 3 (`plan.md`) — "every important mutation is transactional" — without conflating two independently-retriable mutations into one all-or-nothing unit.
4. **Stock reservation model: allocating = decrementing `warehouse_stock.quantity_on_hand`.** The schema has no separate "reserved vs. on-hand" column, so an allocation is modeled as an immediate, real decrement (goods are committed to this order the moment they're allocated), guarded by the existing `warehouse_stock_qty_nonneg` check constraint. Every decrement uses the atomic conditional-update pattern (`UPDATE ... SET quantity_on_hand = quantity_on_hand - :qty WHERE quantity_on_hand >= :qty RETURNING *`) so concurrent orders competing for the same warehouse/product never oversell, with no explicit advisory lock needed.
5. **Re-running `POST /orders/:id/allocate` never touches order items that already carry a manual-override allocation** (`fulfillment_allocations.isManualOverride = true`). Only items with no allocation yet, or only auto-generated (non-override) allocations, are recomputed. This lets Operations force a recompute (e.g. after a backorder consolidation) without silently discarding a rep's deliberate manual choice on other lines — `PUT /orders/:id/allocation` is the only endpoint that ever replaces a manual allocation, and only for the item(s) it targets.
6. **Shipping cost is modeled per warehouse-shipment, not per unit or per line.** `warehouses.shippingCostWeight` is documented in-schema as "a relative weighting, not a currency amount." `plan.md` §5.3's example (`Main Warehouse ₹500`, `East Depot ₹300`, `Estimated shipments: 2`, `Estimated shipping: ₹800`) shows one flat cost per warehouse touched, regardless of how many lines/units come from it. This phase defines `estimatedShipmentCost(warehouse) = warehouse.shippingCostWeight × BASE_SHIPMENT_COST`, a single configurable constant (`FULFILLMENT_BASE_SHIPMENT_COST`, env-tunable, default `100`). Every `fulfillment_allocations` row sharing an `(orderId, warehouseId)` pair stores this same per-warehouse cost (redundant by row, since the schema has no separate shipments table) — order-level "estimated shipments" and "estimated shipping total" are computed by **grouping allocations by `warehouseId`** at read time, never by summing every row, so a warehouse touched by three lines is still counted as one shipment.
7. **The allocation scoring function stays a simple, deterministic greedy pass, per `plan.md`'s explicit "do not build a mathematically complex optimizer."** Per product, candidate warehouses are ranked by `shippingCostWeight` ascending; ties are broken in favor of a warehouse already selected earlier in the same allocation run (consolidation bonus, directly implementing "prefer fewer shipments"). The engine fills from the top-ranked candidate first, spilling into the next only when a candidate's stock is insufficient, and creates a backorder for any quantity no warehouse can cover.
8. **Role model:** Warehouse/stock **configuration** (create warehouse, edit shipping weight, set stock levels) is `ADMIN`-only, mirroring Phase 2's catalog-config pattern. Warehouse **fulfillment actions** (create order, run/re-run allocation, manual override, consolidate backorder) are granted to `SALES_REP` (owner of the underlying quotation only), `SALES_MANAGER`, `FINANCE`, `OPERATIONS`, and `ADMIN` — this reconciles the Problem Statement's role table ("Finance / Operations User ... Manages warehouse fulfillment splits and backorder decisions") with the fact that the B6 Fulfillment screen ("Accept Suggested Split" / "Manual Override") is explicitly listed under the **Sales Rep's own workspace** (§B), so the rep who owns the deal must also be able to act on it. All reads (`GET`) are open to any authenticated internal role, matching Phase 3's quotation-visibility pattern.
9. **Order status derivation is computed from the aggregate of its items' fulfillment state, not stored redundantly per item.** After every allocation/override/consolidation transaction: `FULFILLED` if every order item's allocated quantity equals its ordered quantity (no open backorder anywhere on the order); `BACKORDERED` if not a single unit across the whole order could be allocated; otherwise `PARTIALLY_FULFILLED`. `PENDING_FULFILLMENT` is the pre-allocation default and is never re-entered once allocation has run at least once.
10. **`promisedDeliveryDate`/`estimatedDeliveryDate` (present on `orders` since Phase 1's schema) are simple pass-through fields set at order-creation time**, copied from the quotation's `promisedDeliveryDate` (rep-entered in Phase 3) and defaulted to `today + configurable lead-time days` respectively — no delivery-estimation logic is invented here; Delivery Promise Slippage (comparing the two) is explicitly Phase 8's Deal Health concern, not this phase's.
11. **Fulfillment mutations do not write to `quotations`** — `orders` is a distinct aggregate from `quotationId` on. The only place a quotation row changes here would be if it needed a `FULFILLING` status transition (present in `quotationStatusEnum`), but `plan.md` places that transition alongside portal confirmation in Phase 7's flow, not fulfillment — so it is intentionally **not** written by this phase, avoiding a Phase-3/4-adjacent write from a later phase's module (assumption 2's boundary, extended).

### 4.1 `POST /orders/from-quotation/:quotationId` — order creation (fills the plan.md gap)

- **Purpose:** the missing "quote → order" conversion step; snapshots quotation items into `orders`/`order_items`, then kicks off the first allocation pass.
- **Auth:** owner (`quotation.salesRepId == req.auth.userId`) if `SALES_REP`; unrestricted for `SALES_MANAGER`/`FINANCE`/`OPERATIONS`/`ADMIN`.
- **Validation:** `quotationId` UUID, must resolve to an existing quotation.
- **Idempotency:** the `orders_quotation_id_unique` index is the authority. If an order already exists for this quotation, return it as `200` (not a fresh `201`) with `alreadyExisted:true` in `meta` — never a second insert, never an error on retry.
- **Transaction boundary (txn 1 — creation only):** lock quotation → verify `status='APPROVED'` → lock-check for an existing order → insert `orders` header → insert all `order_items` (one bulk insert) → insert one `audit_logs` row (`entityType='ORDER'`, `action='CREATED_FROM_QUOTATION'`).
- **DB/service flow:**
  1. `tx: SELECT * FROM quotations WHERE id=:quotationId FOR UPDATE`. `404` if missing.
  2. Ownership check (assumption 8) → `403` if a non-owning `SALES_REP`.
  3. `IF quotation.status != 'APPROVED'`: `409 INVALID_STATE` (`'Only an approved quotation can be converted to an order.'`).
  4. `existing = tx.select().from(orders).where(eq(orders.quotationId, quotationId)).first()`. If found, commit txn (no-op) and return it — `200`, `meta:{alreadyExisted:true}`.
  5. `items = tx.select().from(quotationItems).join(products, ...).where(eq(quotationId)).for('update')` — need each item's `productId`, snapshot amounts, and `product.productType` for the `billingLineType` mapping (single joined query, no N+1).
  6. `orderNumber = generateOrderNumber()` (e.g. `ORD-` + zero-padded sequence/timestamp, mirroring Phase 3's `quoteNumber` generation convention).
  7. `tx.insert(orders).values({ orderNumber, quotationId, customerId: quotation.customerId, status:'PENDING_FULFILLMENT', subtotal: quotation.subtotal, discountTotal: quotation.discountTotal, taxTotal: quotation.taxTotal, grandTotal: quotation.grandTotal, promisedDeliveryDate: quotation.promisedDeliveryDate, estimatedDeliveryDate: today() + DEFAULT_LEAD_DAYS }).returning().first()`.
  8. `tx.insert(orderItems).values(items.map(i => ({ orderId: order.id, quotationItemId: i.id, productId: i.productId, quantity: i.quantity, unitPrice: i.unitPrice, discountPct: i.discountPct, discountAmount: i.discountAmount, lineTotal: i.lineTotal, billingLineType: i.product.productType == 'SUBSCRIPTION' ? 'RECURRING' : 'ONE_TIME' })))` — one bulk insert, not a loop of single inserts.
  9. `tx.insert(auditLogs)` — `entityType='ORDER'`, `entityId=order.id`, `action='CREATED_FROM_QUOTATION'`, `newValue:{quotationId, orderNumber, grandTotal}`.
  10. Commit txn 1.
  11. **Txn 2 (best-effort, separate):** `fulfillment.service.allocateOrder(order.id)` (§4.3's engine, run inline here). If it throws, the error is logged and swallowed into the response as `data.allocation = { status:'PENDING', error:'Initial allocation failed, retry via POST /orders/:id/allocate' }` — the order itself is never rolled back over an allocation hiccup (assumption 3).
- **Concurrency:** the quotation row lock in step 1 serializes two concurrent conversion attempts for the same quotation; the second sees the row already exists in step 4 (or the unique index rejects a genuine race with `23505`, mapped to the same idempotent `200` path by re-selecting).
- **Rollback:** any failure in txn 1 rolls back header + items + audit log together — never a headless order or an order with partial items.
- **Success:** `201 { success:true, data:{ order, items, allocation } }` (first creation) or `200` with the same shape + `meta:{alreadyExisted:true}` (idempotent replay).
- **Errors:** `403 FORBIDDEN`, `404 NOT_FOUND`, `409 INVALID_STATE`, `500`.
- **Performance:** 2 point reads + 1 joined read (bounded by item count) + 2 bulk inserts + 1 audit insert, all in one transaction; allocation cost is analyzed in §4.3.

### 4.2 `GET /orders/:id/allocation` — read the current split

- **Purpose:** power the B6 Fulfillment screen table (`plan.md` §5.3): warehouse, quantity, shipping cost, shipment count, plus any backorder line.
- **DB flow (single pass, no N+1):** one query joining `fulfillment_allocations → warehouses → order_items → products` for the order, plus one query joining `backorders → order_items → products` for the same order — two flat, indexed queries total, never one per line.
- **Response shaping (application code, per assumption 6):** group the first result set by `warehouseId` to produce `{ warehouseId, warehouseName, lines:[{orderItemId, productName, quantityAllocated, isManualOverride}], shipmentCost }` (cost taken once per group, not summed across its lines); `estimatedShipments = groups.length`; `estimatedShippingTotal = sum(group.shipmentCost for group in groups)`.
- **Success:** `200 { success:true, data:{ orderId, status, warehouseSplits:[...], estimatedShipments, estimatedShippingTotal, backorders:[{orderItemId, productName, quantityRequested, quantityFulfilled, quantityBackordered, status}] } }`.
- **Errors:** `403 FORBIDDEN`, `404 NOT_FOUND`.
- **Performance:** 2 indexed queries (`fulfillment_allocations_order_id_idx`, `backorders` via `order_items.order_id`), grouping done in memory over a small, order-sized result set.

### 4.3 `POST /orders/:id/allocate` — the auto allocation engine

- **Purpose:** implement `allocateOrder(orderId)` exactly as named in `plan.md` §5.2.
- **Idempotency:** safe to call repeatedly — each run only (re)computes items that don't already carry a manual-override allocation (assumption 5); an item already fully, manually allocated is left untouched and reported as-is.
- **Transaction boundary:** one transaction per call: lock order → lock target order items → for each, release any existing non-override allocations (restore stock) → re-fetch live stock → greedy-fill via the scoring function → atomically decrement stock per chosen warehouse → upsert `fulfillment_allocations` rows → upsert/resolve `backorders` → recompute and write `order.status` → one `audit_logs` row.
- **DB/service flow:**
  1. `tx: SELECT * FROM orders WHERE id=:id FOR UPDATE`. `404` if missing.
  2. Ownership check via `orders.quotationId → quotations.salesRepId` (one join, not a second round trip — carried in the same `SELECT`).
  3. `items = tx.select().from(orderItems).where(eq(orderId)).for('update')`.
  4. `targetItems = items.filter(i => NOT existingManualOverrideExistsFor(i.id))` (existing allocations fetched in the same pass as step 3 via a join to `fulfillment_allocations`).
  5. For each item in `targetItems` with existing **non-override** allocations: `releaseStock(tx, existingAllocations)` — for each, `UPDATE warehouse_stock SET quantity_on_hand = quantity_on_hand + :qty WHERE warehouse_id=:w AND product_id=:p`; then `DELETE FROM fulfillment_allocations WHERE id IN (...)`.
  6. `stockByProduct = tx.select().from(warehouseStock).innerJoin(warehouses, ...).where(inArray(productId, targetItems.map(i=>i.productId)) AND warehouses.isActive).orderBy(...)` — **one batched query** for every distinct product needed, never one query per line.
  7. For each `item` in `targetItems`, call the pure engine: `plan = allocationEngine.planAllocation({ requestedQty: item.quantity, candidates: stockByProduct[item.productId], alreadyTouchedWarehouseIds: runningSet })` → `{ allocations:[{warehouseId, qty}], shortfall }` (§5.5 for the algorithm). Add `plan.allocations`' warehouse ids to `runningSet` for the consolidation tie-break on subsequent items.
  8. For each `{warehouseId, qty}` in `plan.allocations`: `decremented = tx.execute("UPDATE warehouse_stock SET quantity_on_hand = quantity_on_hand - :qty WHERE warehouse_id=:w AND product_id=:p AND quantity_on_hand >= :qty RETURNING *")`. If zero rows affected (lost a race since step 6's read), **re-fetch that one product's live stock and retry the fill for the remaining unfulfilled quantity against the next-best candidate** (bounded retry — at most `candidates.length` attempts per item); if still short, that amount becomes shortfall.
  9. `tx.insert(fulfillmentAllocations).values(...)` — one bulk insert for all `(item, warehouse, qty)` tuples decided this run, `shippingCost` = `estimatedShipmentCost(warehouse)` per assumption 6, `isManualOverride:false`.
  10. `IF plan.shortfall > 0`: upsert a `backorders` row for the item (`quantityRequested=item.quantity`, `quantityFulfilled = item.quantity - plan.shortfall`, `quantityBackordered = plan.shortfall`, `status = quantityFulfilled==0 ? 'OPEN' : 'PARTIALLY_FULFILLED'`); if an open backorder already existed for the item, update it instead of inserting a duplicate.
  11. **ELSE** (fully covered): if an open/partially-fulfilled backorder row exists for the item, mark it `FULFILLED`, `resolvedAt=now()`.
  12. After all items processed: `newStatus = deriveOrderStatus(allItemsForOrder)` (assumption 9) → `tx.update(orders).set({ status:newStatus, updatedAt:now() })`.
  13. `tx.insert(auditLogs)` — `entityType='ORDER'`, `action='AUTO_ALLOCATED'`, `newValue:{ status:newStatus, itemsAllocated: targetItems.length }`.
- **Concurrency:** the `orders` row lock (step 1) plus the `order_items ... FOR UPDATE` lock (step 3) serialize any second concurrent `allocate`/override call on the same order. Cross-order races over the *same warehouse stock* are handled independently by the conditional decrement in step 8 (assumption 4) — no cross-order lock is needed since correctness is enforced at the row level by Postgres itself.
- **Rollback:** any failure — including exhausting retries in step 8 — rolls back the entire transaction: no partial release-without-reallocate, no orphaned `fulfillment_allocations` row without a matching stock decrement.
- **Success:** `200 { success:true, data:{ order:{id,status}, allocation:<same shape as §4.2's GET> } }`.
- **Errors:** `403 FORBIDDEN`, `404 NOT_FOUND`, `500`.
- **Performance:** flat cost regardless of order size beyond the number of distinct products (step 6 is one batched query; steps 8–11 are per-line but bounded by items-per-order, which is small — never a per-line extra `SELECT`).

### 4.4 `PUT /orders/:id/allocation` — manual override

- **Purpose:** `plan.md` §5.3's "Manual Override" button — the rep/ops user specifies exactly which warehouse(s) fulfill which order item(s).
- **Body:** `{ overrides: [ { orderItemId, splits: [ { warehouseId, quantity } ] } ] }`.
- **Validation:** every `orderItemId` belongs to this order; every `warehouseId` is active; every `quantity` is a positive integer; `sum(splits.quantity) <= orderItem.quantity` for each item (the remainder, if any, becomes/stays a backorder — overriding to less than the full quantity is allowed and intentional, matching "Manual Override" as a deliberate rep choice, not a forced full-cover).
- **Idempotency:** not naturally idempotent (a specific new split is a deliberate command), but safely retryable — replaying the identical body after a prior success is a no-op release-then-reapply of the same numbers, ending in the same state.
- **Transaction boundary:** one transaction: lock order → lock targeted order items → release *all* existing allocations (both auto and prior manual) for the targeted items only → validate requested split against freshly-read stock → atomically decrement per split → insert new `fulfillment_allocations` rows (`isManualOverride:true`) → upsert/resolve backorders for any remainder → recompute `order.status` → one `audit_logs` row (`action='MANUAL_OVERRIDE'`, `oldValue`/`newValue` = prior vs. new split per item, satisfying `plan.md` §A3's "all ... edits must be logged").
- **DB/service flow:**
  1. `tx: SELECT * FROM orders WHERE id=:id FOR UPDATE` + ownership check (as §4.3).
  2. `targetItemIds = overrides.map(o => o.orderItemId)`; `tx.select().from(orderItems).where(and(eq(orderId), inArray(id, targetItemIds))).for('update')` — verify every id resolves and belongs to this order, else `400 VALIDATION_FAILED`.
  3. `existingAllocations = tx.select().from(fulfillmentAllocations).where(inArray(orderItemId, targetItemIds))` (captured now, for the audit `oldValue` and for the release step).
  4. `releaseStock(tx, existingAllocations)` (same helper as §4.3 step 5) → `DELETE FROM fulfillment_allocations WHERE order_item_id IN (...)`.
  5. For each `override` in body: for each `split`, atomically decrement via the same conditional-`UPDATE ... RETURNING` as §4.3 step 8. **If any single decrement in this whole request fails (insufficient live stock), abort and roll back the entire transaction** — a manual override is an explicit human commitment; silently under-fulfilling part of it while another part succeeds would misrepresent what the user asked for. Return `409 INSUFFICIENT_STOCK` with `details:{orderItemId, warehouseId, requested, available}` naming the first failing split.
  6. `tx.insert(fulfillmentAllocations)` — bulk insert all validated splits, `isManualOverride:true`, `shippingCost` per assumption 6.
  7. For each targeted item: `remainder = item.quantity - sum(its splits)`; upsert/resolve its `backorders` row exactly as §4.3 steps 10–11.
  8. Recompute `order.status` (assumption 9) → `tx.update(orders)`.
  9. `tx.insert(auditLogs)` — `entityType='ORDER'`, `action='MANUAL_OVERRIDE'`, `oldValue:{allocations: existingAllocations}`, `newValue:{allocations: newAllocations}`.
- **Concurrency:** same row-lock chain as §4.3; the all-or-nothing decrement in step 5 means a losing race against a concurrent auto-allocate/override on a *different* order sharing the same warehouse stock simply surfaces as `409 INSUFFICIENT_STOCK` for a retry, never a torn/partial commit.
- **Rollback:** any failure rolls back the release + every decrement + every insert together — the pre-override allocation state is fully restored on error, never left half-released.
- **Success:** `200 { success:true, data:{ order:{id,status}, allocation:<§4.2 shape> } }`.
- **Errors:** `400 VALIDATION_FAILED`, `403 FORBIDDEN`, `404 NOT_FOUND`, `409 INSUFFICIENT_STOCK`, `500`.
- **Performance:** bounded by the number of `(item, split)` pairs in the request body — one batched release, N conditional decrements (N = total splits requested, typically ≤ a handful), one bulk insert.

### 4.5 `POST /orders/:id/backorder/consolidate` — the bonus flow

- **Purpose:** `plan.md` §5.4 bonus — "New stock detected ... [Consolidate Remaining Backorder]." A manual re-check trigger (no background job, per Rule 5/`plan.md`'s explicit P2 deprioritization of queues/cron); assumes an Admin has already restocked via `PUT /warehouses/:id/stock/:productId`.
- **Idempotency:** safe to call repeatedly — a backorder with nothing newly fulfillable is simply left unchanged (`200` with an empty `resolved` list).
- **Transaction boundary:** one transaction: lock order → lock its `OPEN`/`PARTIALLY_FULFILLED` backorders → for each, re-run the same greedy fill (§5.5) against current stock for the *outstanding* quantity only → decrement stock → insert incremental `fulfillment_allocations` rows → update the backorder row → recompute `order.status` → one `audit_logs` row.
- **DB/service flow:**
  1. `tx: SELECT * FROM orders WHERE id=:id FOR UPDATE` + ownership check.
  2. `openBackorders = tx.select().from(backorders).innerJoin(orderItems, ...).where(eq(orderId) AND status IN ('OPEN','PARTIALLY_FULFILLED')).for('update')`. `IF empty`: return `200` with `resolved: []` immediately (idempotent no-op — nothing to consolidate).
  3. `stockByProduct = tx.select()...` batched exactly as §4.3 step 6, scoped to the products on these backorders only.
  4. For each backorder: `plan = allocationEngine.planAllocation({ requestedQty: backorder.quantityBackordered, candidates: stockByProduct[item.productId], alreadyTouchedWarehouseIds: runningSet })`.
  5. `IF plan.allocations is empty`: leave this backorder untouched, continue to the next.
  6. `ELSE`: decrement stock per allocation (same conditional pattern), `tx.insert(fulfillmentAllocations)` for the newly-covered portion (`isManualOverride:false`), `tx.update(backorders)` — `quantityFulfilled += covered`, `quantityBackordered -= covered`, `status = quantityBackordered==0 ? 'FULFILLED' : 'PARTIALLY_FULFILLED'`, `resolvedAt = quantityBackordered==0 ? now() : null`.
  7. Recompute `order.status` (assumption 9) once, after the loop.
  8. `tx.insert(auditLogs)` — `entityType='ORDER'`, `action='BACKORDER_CONSOLIDATED'`, `newValue:{resolvedCount, orderStatus:newStatus}`.
- **Concurrency:** identical lock chain to §4.3/§4.4; the conditional decrement remains the sole cross-order race guard.
- **Rollback:** any failure rolls back every partial consolidation in the batch together — a backorder is never left in a state that doesn't match its own `fulfillment_allocations` rows.
- **Success:** `200 { success:true, data:{ order:{id,status}, resolved:[{orderItemId, productName, newlyFulfilled, remainingBackordered}] } }`.
- **Errors:** `403 FORBIDDEN`, `404 NOT_FOUND`, `500`.
- **Performance:** one batched stock read regardless of backorder count; per-backorder cost is O(candidate warehouses), bounded and small.

### 4.6 Warehouse config endpoints (§5.1) — brief spec

- `GET /warehouses` / `GET /warehouses/:id` / `GET /warehouses/:id/stock`: plain paginated reads, same `parseListQuery`/`buildMeta` convention as every other list endpoint since Phase 2. No transaction needed.
- `POST /warehouses`: `{ name, location?, shippingCostWeight? }`. `name` unique (`warehouses_name_unique`) → `409 NAME_TAKEN` on `23505`. Single insert, no transaction needed (single-statement mutation).
- `PATCH /warehouses/:id`: partial update of `name`/`location`/`shippingCostWeight`/`isActive`. Setting `isActive:false` is a soft-disable — the allocation engine's candidate query (`WHERE warehouses.isActive`) already excludes it going forward; existing allocations against it are untouched (no cascading side effect invented here).
- `PUT /warehouses/:id/stock/:productId`: `{ quantityOnHand, reorderThreshold? }`. Upsert on the `warehouse_stock_warehouse_product_unique` constraint (`ON CONFLICT (warehouseId, productId) DO UPDATE`). This is an **absolute set** (admin replenishment/config entry), not a delta — documented as an MVP-acceptable, admin-only, infrequent action; a concurrent allocation decrementing the same row mid-update simply results in last-write-wins on `quantityOnHand`, consistent with Phase 2's stated "no optimistic-concurrency column" posture for admin config writes (Phase 2 assumption 8, carried forward). `quantityOnHand < 0` → `400 VALIDATION_FAILED` (the DB check constraint is the final backstop, not the primary guard).

**File: `server/src/modules/fulfillment/fulfillment.allocationEngine.js`**
```
MODULE fulfillment.allocationEngine
IMPORT { env } FROM '../../config/env.js'

CONST BASE_SHIPMENT_COST = env.fulfillmentBaseShipmentCost OR 100   // currency units per weight-1 shipment

// candidates: [{ warehouseId, quantityOnHand, shippingCostWeight }], already filtered to isActive
// alreadyTouchedWarehouseIds: Set<uuid> — warehouses used elsewhere in this same run, for the
// consolidation tie-break (assumption 7: prefer fewer distinct shipments).
FUNCTION rankCandidates(candidates, alreadyTouchedWarehouseIds):
    RETURN [...candidates].sort((a, b) => {
        aTouched = alreadyTouchedWarehouseIds.has(a.warehouseId) ? 0 : 1
        bTouched = alreadyTouchedWarehouseIds.has(b.warehouseId) ? 0 : 1
        IF aTouched != bTouched: RETURN aTouched - bTouched      // touched-first
        RETURN a.shippingCostWeight - b.shippingCostWeight        // then cheapest shipping
    })

// Pure function — greedy fill, no I/O. Caller re-derives `candidates` fresh from the DB
// immediately before calling this (assumption 4), and re-validates via the atomic
// conditional decrement afterward — this function only decides the *plan*.
FUNCTION planAllocation({ requestedQty, candidates, alreadyTouchedWarehouseIds = new Set() }):
    ranked = rankCandidates(candidates, alreadyTouchedWarehouseIds)
    remaining = requestedQty
    allocations = []
    FOR candidate IN ranked:
        IF remaining <= 0: BREAK
        IF candidate.quantityOnHand <= 0: CONTINUE
        take = MIN(remaining, candidate.quantityOnHand)
        allocations.push({ warehouseId: candidate.warehouseId, qty: take })
        remaining -= take
    RETURN { allocations, shortfall: remaining }

FUNCTION estimatedShipmentCost(shippingCostWeight):
    RETURN round2(shippingCostWeight * BASE_SHIPMENT_COST)

EXPORT { planAllocation, estimatedShipmentCost, rankCandidates }
```

```
MODULE fulfillment.repository
IMPORT { orders, orderItems, warehouses, warehouseStock, fulfillmentAllocations, backorders, auditLogs }
    FROM '../../db/schema/index.js'
IMPORT { quotations } FROM '../../db/schema/index.js'
IMPORT { eq, and, inArray, sql } FROM 'drizzle-orm'

FUNCTION lockOrderForUpdate(tx, orderId):
    RETURN tx.select({ order: orders, salesRepId: quotations.salesRepId })
             .from(orders).innerJoin(quotations, eq(orders.quotationId, quotations.id))
             .where(eq(orders.id, orderId)).for('update').first()

FUNCTION findByQuotationId(tx, quotationId) ->
    tx.select().from(orders).where(eq(orders.quotationId, quotationId)).first()

FUNCTION lockOrderItems(tx, orderId, itemIds = null):
    conditions = [eq(orderItems.orderId, orderId)]
    IF itemIds: conditions.push(inArray(orderItems.id, itemIds))
    RETURN tx.select().from(orderItems).where(and(...conditions)).for('update')

FUNCTION existingAllocationsForItems(tx, itemIds) ->
    tx.select().from(fulfillmentAllocations).where(inArray(fulfillmentAllocations.orderItemId, itemIds))

// Batched stock read for every distinct product needed — never called per-line.
FUNCTION batchedStockCandidates(tx, productIds):
    rows = tx.select({ productId, warehouseId: warehouseStock.warehouseId,
                        quantityOnHand, shippingCostWeight: warehouses.shippingCostWeight })
             .from(warehouseStock).innerJoin(warehouses, eq(warehouseStock.warehouseId, warehouses.id))
             .where(and(inArray(warehouseStock.productId, productIds), eq(warehouses.isActive, true)))
    RETURN groupBy(rows, 'productId')   // Map<productId, [{warehouseId, quantityOnHand, shippingCostWeight}]>

// Restores stock for a set of allocation rows being replaced/removed, then deletes them.
FUNCTION releaseAllocations(tx, allocationRows):
    FOR row IN allocationRows:
        tx.update(warehouseStock)
          .set({ quantityOnHand: sql`${warehouseStock.quantityOnHand} + ${row.quantityAllocated}`, updatedAt: now() })
          .where(and(eq(warehouseId, row.warehouseId), eq(productId, row.productId)))
    tx.delete(fulfillmentAllocations).where(inArray(id, allocationRows.map(r => r.id)))

// The single race-safe primitive every allocation path uses.
// Returns the updated row, or null if the conditional check failed (lost the race).
FUNCTION tryDecrementStock(tx, warehouseId, productId, qty):
    rows = tx.execute(sql`
        UPDATE warehouse_stock SET quantity_on_hand = quantity_on_hand - ${qty}, updated_at = now()
        WHERE warehouse_id = ${warehouseId} AND product_id = ${productId} AND quantity_on_hand >= ${qty}
        RETURNING *`)
    RETURN rows[0] OR null

FUNCTION insertAllocations(tx, rows) -> tx.insert(fulfillmentAllocations).values(rows).returning()

FUNCTION upsertBackorder(tx, orderItemId, { quantityRequested, quantityFulfilled, quantityBackordered, status }):
    existing = tx.select().from(backorders)
                 .where(and(eq(orderItemId), inArray(status, ['OPEN','PARTIALLY_FULFILLED']))).for('update').first()
    IF existing:
        RETURN tx.update(backorders).set({ quantityFulfilled, quantityBackordered, status,
                    resolvedAt: status=='FULFILLED' ? now() : null }).where(eq(id, existing.id)).returning().first()
    RETURN tx.insert(backorders).values({ orderItemId, quantityRequested, quantityFulfilled, quantityBackordered, status,
                    resolvedAt: status=='FULFILLED' ? now() : null }).returning().first()

FUNCTION resolveBackorderIfOpen(tx, orderItemId):
    tx.update(backorders).set({ status:'FULFILLED', resolvedAt: now() })
      .where(and(eq(orderItemId), inArray(status, ['OPEN','PARTIALLY_FULFILLED'])))

FUNCTION openBackordersForOrder(tx, orderId):
    RETURN tx.select({ backorder: backorders, orderItem: orderItems })
             .from(backorders).innerJoin(orderItems, eq(backorders.orderItemId, orderItems.id))
             .where(and(eq(orderItems.orderId, orderId), inArray(backorders.status, ['OPEN','PARTIALLY_FULFILLED'])))
             .for('update')

FUNCTION allItemsWithFulfillmentState(tx, orderId):
    // one joined read: each item + its total allocated qty + whether it has an open backorder
    RETURN tx.select({
        item: orderItems,
        allocatedQty: sql`COALESCE(SUM(${fulfillmentAllocations.quantityAllocated}), 0)`,
        hasOpenBackorder: sql`EXISTS (SELECT 1 FROM backorders WHERE order_item_id = ${orderItems.id}
                                      AND status IN ('OPEN','PARTIALLY_FULFILLED'))`
    }).from(orderItems)
      .leftJoin(fulfillmentAllocations, eq(fulfillmentAllocations.orderItemId, orderItems.id))
      .where(eq(orderItems.orderId, orderId))
      .groupBy(orderItems.id)

FUNCTION updateOrderStatus(tx, orderId, status) ->
    tx.update(orders).set({ status, updatedAt: now() }).where(eq(orders.id, orderId))

FUNCTION insertAuditLog(tx, { actorId, entityId, action, oldValue, newValue }) ->
    tx.insert(auditLogs).values({ actorId, entityType:'ORDER', entityId, action, oldValue, newValue })

// Full read for GET /orders/:id/allocation — two flat queries, grouped in application code.
FUNCTION readAllocationView(orderId):
    allocations = db.select({
        warehouseId, warehouseName: warehouses.name, orderItemId, productName: products.name,
        quantityAllocated, isManualOverride, shippingCost
    }).from(fulfillmentAllocations)
      .innerJoin(warehouses, eq(fulfillmentAllocations.warehouseId, warehouses.id))
      .innerJoin(orderItems, eq(fulfillmentAllocations.orderItemId, orderItems.id))
      .innerJoin(products, eq(orderItems.productId, products.id))
      .where(eq(fulfillmentAllocations.orderId, orderId))
    backorderRows = db.select({
        orderItemId, productName: products.name, quantityRequested, quantityFulfilled, quantityBackordered, status
    }).from(backorders).innerJoin(orderItems, eq(backorders.orderItemId, orderItems.id))
      .innerJoin(products, eq(orderItems.productId, products.id))
      .where(eq(orderItems.orderId, orderId))
    RETURN { allocations, backorderRows }
```

```
MODULE fulfillment.service
IMPORT * as repo FROM './fulfillment.repository.js'
IMPORT * as quotationsRepo FROM '../quotations/quotations.repository.js'   // Phase 3, read-only cross-call
IMPORT * as engine FROM './fulfillment.allocationEngine.js'
IMPORT { NotFoundError, ForbiddenError, ConflictError } FROM '../../common/errors.js'
IMPORT { getDb } FROM '../../config/database.js'
IMPORT { env } FROM '../../config/env.js'

CONST DEFAULT_LEAD_DAYS = 5

FUNCTION assertAccess(auth, salesRepId):
    IF auth.role == 'SALES_REP' AND salesRepId != auth.userId: THROW ForbiddenError()

// ---- §4.1 order creation ----
FUNCTION createOrderFromQuotation(quotationId, auth):
    db = getDb()
    order = await db.transaction(async (tx) => {
        quotation = await quotationsRepo.lockForUpdate(tx, quotationId)     // Phase 3 export, reused read-only
        IF NOT quotation: THROW NotFoundError('Quotation')
        assertAccess(auth, quotation.salesRepId)

        existing = await repo.findByQuotationId(tx, quotationId)
        IF existing:
            RETURN { order: existing, alreadyExisted: true }

        IF quotation.status != 'APPROVED':
            THROW ConflictError('INVALID_STATE', 'Only an approved quotation can be converted to an order.')

        items = await quotationsRepo.itemsWithProductType(tx, quotationId)   // joined read, incl. product.productType
        orderNumber = await generateOrderNumber(tx)
        newOrder = await tx.insert(orders).values({
            orderNumber, quotationId, customerId: quotation.customerId, status: 'PENDING_FULFILLMENT',
            subtotal: quotation.subtotal, discountTotal: quotation.discountTotal, taxTotal: quotation.taxTotal,
            grandTotal: quotation.grandTotal, promisedDeliveryDate: quotation.promisedDeliveryDate,
            estimatedDeliveryDate: addDays(today(), DEFAULT_LEAD_DAYS)
        }).returning().first()

        await tx.insert(orderItems).values(items.map(i => ({
            orderId: newOrder.id, quotationItemId: i.id, productId: i.productId, quantity: i.quantity,
            unitPrice: i.unitPrice, discountPct: i.discountPct, discountAmount: i.discountAmount,
            lineTotal: i.lineTotal, billingLineType: i.productType == 'SUBSCRIPTION' ? 'RECURRING' : 'ONE_TIME'
        })))

        await repo.insertAuditLog(tx, { actorId: auth.userId, entityId: newOrder.id,
            action: 'CREATED_FROM_QUOTATION', newValue: { quotationId, orderNumber, grandTotal: quotation.grandTotal } })

        RETURN { order: newOrder, alreadyExisted: false }
    })

    allocation = null
    TRY:
        allocation = await allocateOrder(order.order.id, auth, { skipAccessCheck: true })
    CATCH e:
        log.error('Initial allocation failed for order ' + order.order.id, e)
        allocation = { status: 'PENDING', error: 'Initial allocation failed, retry via POST /orders/:id/allocate' }

    RETURN { order: order.order, alreadyExisted: order.alreadyExisted, allocation }

// ---- shared: derive order.status from item-level fulfillment state ----
FUNCTION deriveOrderStatus(itemStates):     // [{ item, allocatedQty, hasOpenBackorder }]
    fullyCovered = itemStates.every(s => s.allocatedQty >= s.item.quantity AND NOT s.hasOpenBackorder)
    IF fullyCovered: RETURN 'FULFILLED'
    nothingAllocated = itemStates.every(s => s.allocatedQty == 0)
    IF nothingAllocated: RETURN 'BACKORDERED'
    RETURN 'PARTIALLY_FULFILLED'

// ---- §4.3 auto allocation engine ----
FUNCTION allocateOrder(orderId, auth, { skipAccessCheck = false } = {}):
    db = getDb()
    RETURN db.transaction(async (tx) => {
        locked = await repo.lockOrderForUpdate(tx, orderId)
        IF NOT locked: THROW NotFoundError('Order')
        IF NOT skipAccessCheck: assertAccess(auth, locked.salesRepId)

        allItems = await repo.lockOrderItems(tx, orderId)
        existingAllocs = await repo.existingAllocationsForItems(tx, allItems.map(i => i.id))
        overriddenItemIds = new Set(existingAllocs.filter(a => a.isManualOverride).map(a => a.orderItemId))
        targetItems = allItems.filter(i => NOT overriddenItemIds.has(i.id))

        nonOverrideAllocs = existingAllocs.filter(a => NOT a.isManualOverride
                                                        AND targetItems.some(i => i.id == a.orderItemId))
        IF nonOverrideAllocs.length: await repo.releaseAllocations(tx, nonOverrideAllocs)

        candidatesByProduct = await repo.batchedStockCandidates(tx, targetItems.map(i => i.productId))

        runningTouched = new Set()
        newAllocationRows = []
        FOR item IN targetItems:
            plan = await fillWithRetry(tx, item, candidatesByProduct[item.productId] OR [], runningTouched)
            FOR alloc IN plan.allocations:
                runningTouched.add(alloc.warehouseId)
                newAllocationRows.push({ orderId, orderItemId: item.id, warehouseId: alloc.warehouseId,
                    quantityAllocated: alloc.qty, isManualOverride: false,
                    shippingCost: engine.estimatedShipmentCost(candidateWeight(candidatesByProduct[item.productId], alloc.warehouseId)) })
            IF plan.shortfall > 0:
                await repo.upsertBackorder(tx, item.id, { quantityRequested: item.quantity,
                    quantityFulfilled: item.quantity - plan.shortfall, quantityBackordered: plan.shortfall,
                    status: (item.quantity - plan.shortfall) == 0 ? 'OPEN' : 'PARTIALLY_FULFILLED' })
            ELSE:
                await repo.resolveBackorderIfOpen(tx, item.id)

        IF newAllocationRows.length: await repo.insertAllocations(tx, newAllocationRows)

        states = await repo.allItemsWithFulfillmentState(tx, orderId)
        newStatus = deriveOrderStatus(states)
        await repo.updateOrderStatus(tx, orderId, newStatus)
        await repo.insertAuditLog(tx, { actorId: auth?.userId, entityId: orderId, action: 'AUTO_ALLOCATED',
            newValue: { status: newStatus, itemsAllocated: targetItems.length } })

        RETURN buildAllocationView(orderId, newStatus, tx)
    })

// Bounded retry against a losing race on the first-choice warehouse (assumption 4/step 8).
FUNCTION fillWithRetry(tx, item, candidates, runningTouched):
    remaining = item.quantity
    collected = []
    workingCandidates = [...candidates]
    WHILE remaining > 0 AND workingCandidates.length > 0:
        plan = engine.planAllocation({ requestedQty: remaining, candidates: workingCandidates, alreadyTouchedWarehouseIds: runningTouched })
        FOR alloc IN plan.allocations:
            row = await repo.tryDecrementStock(tx, alloc.warehouseId, item.productId, alloc.qty)
            IF row:
                collected.push(alloc)
                remaining -= alloc.qty
            ELSE:
                // lost the race — drop this candidate and retry the loop against the rest
                workingCandidates = workingCandidates.filter(c => c.warehouseId != alloc.warehouseId)
    RETURN { allocations: collected, shortfall: remaining }

// ---- §4.4 manual override ----
FUNCTION overrideAllocation(orderId, overrides, auth):
    db = getDb()
    RETURN db.transaction(async (tx) => {
        locked = await repo.lockOrderForUpdate(tx, orderId)
        IF NOT locked: THROW NotFoundError('Order')
        assertAccess(auth, locked.salesRepId)

        itemIds = overrides.map(o => o.orderItemId)
        items = await repo.lockOrderItems(tx, orderId, itemIds)
        IF items.length != itemIds.length: THROW ValidationError(['One or more orderItemId values are invalid for this order.'])

        existingAllocs = await repo.existingAllocationsForItems(tx, itemIds)
        IF existingAllocs.length: await repo.releaseAllocations(tx, existingAllocs)

        newRows = []
        FOR override IN overrides:
            item = items.find(i => i.id == override.orderItemId)
            totalRequested = sum(override.splits.map(s => s.quantity))
            IF totalRequested > item.quantity: THROW ValidationError([`Requested split exceeds ordered quantity for item ${item.id}.`])
            FOR split IN override.splits:
                row = await repo.tryDecrementStock(tx, split.warehouseId, item.productId, split.quantity)
                IF NOT row:
                    available = await repo.currentStock(tx, split.warehouseId, item.productId)
                    THROW ConflictError('INSUFFICIENT_STOCK', 'Not enough stock for the requested override.',
                        { orderItemId: item.id, warehouseId: split.warehouseId, requested: split.quantity, available })
                newRows.push({ orderId, orderItemId: item.id, warehouseId: split.warehouseId,
                    quantityAllocated: split.quantity, isManualOverride: true,
                    shippingCost: engine.estimatedShipmentCost(row.shippingCostWeightOfWarehouse) })
            remainder = item.quantity - totalRequested
            IF remainder > 0:
                await repo.upsertBackorder(tx, item.id, { quantityRequested: item.quantity,
                    quantityFulfilled: totalRequested, quantityBackordered: remainder,
                    status: totalRequested == 0 ? 'OPEN' : 'PARTIALLY_FULFILLED' })
            ELSE:
                await repo.resolveBackorderIfOpen(tx, item.id)

        IF newRows.length: await repo.insertAllocations(tx, newRows)

        states = await repo.allItemsWithFulfillmentState(tx, orderId)
        newStatus = deriveOrderStatus(states)
        await repo.updateOrderStatus(tx, orderId, newStatus)
        await repo.insertAuditLog(tx, { actorId: auth.userId, entityId: orderId, action: 'MANUAL_OVERRIDE',
            oldValue: { allocations: existingAllocs }, newValue: { allocations: newRows } })

        RETURN buildAllocationView(orderId, newStatus, tx)
    })
    // Any thrown error (including INSUFFICIENT_STOCK) rolls back every decrement/release/insert in this txn.

// ---- §4.5 backorder consolidation ----
FUNCTION consolidateBackorders(orderId, auth):
    db = getDb()
    RETURN db.transaction(async (tx) => {
        locked = await repo.lockOrderForUpdate(tx, orderId)
        IF NOT locked: THROW NotFoundError('Order')
        assertAccess(auth, locked.salesRepId)

        openBackorders = await repo.openBackordersForOrder(tx, orderId)
        IF openBackorders.empty: RETURN { order: { id: orderId, status: locked.order.status }, resolved: [] }

        candidatesByProduct = await repo.batchedStockCandidates(tx, openBackorders.map(b => b.orderItem.productId))
        runningTouched = new Set()
        resolved = []
        FOR entry IN openBackorders:
            plan = await fillWithRetry(tx, { id: entry.orderItem.id, productId: entry.orderItem.productId,
                                              quantity: entry.backorder.quantityBackordered },
                                        candidatesByProduct[entry.orderItem.productId] OR [], runningTouched)
            covered = entry.backorder.quantityBackordered - plan.shortfall
            IF covered > 0:
                FOR alloc IN plan.allocations:
                    runningTouched.add(alloc.warehouseId)
                await repo.insertAllocations(tx, plan.allocations.map(a => ({
                    orderId, orderItemId: entry.orderItem.id, warehouseId: a.warehouseId, quantityAllocated: a.qty,
                    isManualOverride: false, shippingCost: engine.estimatedShipmentCost(candidateWeight(candidatesByProduct[entry.orderItem.productId], a.warehouseId))
                })))
                newFulfilled = entry.backorder.quantityFulfilled + covered
                newBackordered = entry.backorder.quantityBackordered - covered
                await repo.upsertBackorder(tx, entry.orderItem.id, { quantityRequested: entry.backorder.quantityRequested,
                    quantityFulfilled: newFulfilled, quantityBackordered: newBackordered,
                    status: newBackordered == 0 ? 'FULFILLED' : 'PARTIALLY_FULFILLED' })
                resolved.push({ orderItemId: entry.orderItem.id, newlyFulfilled: covered, remainingBackordered: newBackordered })

        states = await repo.allItemsWithFulfillmentState(tx, orderId)
        newStatus = deriveOrderStatus(states)
        await repo.updateOrderStatus(tx, orderId, newStatus)
        await repo.insertAuditLog(tx, { actorId: auth.userId, entityId: orderId, action: 'BACKORDER_CONSOLIDATED',
            newValue: { resolvedCount: resolved.length, orderStatus: newStatus } })

        RETURN { order: { id: orderId, status: newStatus }, resolved }
    })

// ---- read view (GET /orders/:id and /orders/:id/allocation share this shape) ----
FUNCTION getAllocationView(orderId, auth):
    order = await ordersHeaderWithAccessCheck(orderId, auth)     // 404/403 guard, reused by GET /orders/:id too
    { allocations, backorderRows } = repo.readAllocationView(orderId)
    groups = groupBy(allocations, 'warehouseId')
    warehouseSplits = Object.values(groups).map(g => ({
        warehouseId: g[0].warehouseId, warehouseName: g[0].warehouseName,
        lines: g.map(l => ({ orderItemId: l.orderItemId, productName: l.productName,
                              quantityAllocated: l.quantityAllocated, isManualOverride: l.isManualOverride })),
        shipmentCost: g[0].shippingCost      // same value on every row in the group, per assumption 6 — take once
    }))
    RETURN {
        orderId, status: order.status, warehouseSplits,
        estimatedShipments: warehouseSplits.length,
        estimatedShippingTotal: sum(warehouseSplits.map(w => w.shipmentCost)),
        backorders: backorderRows
    }
```

```
MODULE fulfillment.validator

FUNCTION validateOverride(body):
    errors = []
    IF NOT Array.isArray(body.overrides) OR body.overrides.empty:
        errors.push('overrides must be a non-empty array.')
        RETURN { valid:false, errors, clean:null }
    clean = []
    FOR o IN body.overrides:
        IF NOT isUuid(o.orderItemId): errors.push('Each override needs a valid orderItemId.')
        IF NOT Array.isArray(o.splits) OR o.splits.empty: errors.push(`orderItemId ${o.orderItemId} needs at least one split.`)
        cleanSplits = []
        FOR s IN (o.splits OR []):
            qty = int(s.quantity)
            IF NOT isUuid(s.warehouseId): errors.push('Each split needs a valid warehouseId.')
            IF NOT isInteger(qty) OR qty <= 0: errors.push('Each split quantity must be a positive integer.')
            cleanSplits.push({ warehouseId: s.warehouseId, quantity: qty })
        clean.push({ orderItemId: o.orderItemId, splits: cleanSplits })
    RETURN { valid: errors.empty, errors, clean: { overrides: clean } }
```
