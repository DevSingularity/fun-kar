# DealFlow360 — Phase 2 API Design
## Backend Configuration + Admin Control Plane (`plan.md` Hour 1–2)

Builds directly on Phase 1's auth/RBAC/response-envelope foundation. Scope is
strictly §2.1–2.5 of `plan.md`: Product Management, Customer Management,
Price Lists, Discount Governance, and the `evaluateQuoteRisk` engine.
Quotation submission (3.4), approve/reject actions (4.2), and the upsell
engine (4.1) are **not** built here — `plan.md` places them in Phases 3–4,
and they depend on tables (`quotations`, `approval_requests`) that don't
have any writer yet.

---

## 1. Assumptions carried into this phase

1. **Role mapping follows the Problem Statement's role descriptions
   literally**, since `plan.md` doesn't restate them per-endpoint:
   - Product / Category / Price-List config → PS §3 "Admin: Manages backend
     setup: products, price lists...". Restricted to `ADMIN` only.
   - Discount tiers / category ceilings / approval chain → PS §3 explicitly
     gives this to **both** "Sales Manager/Approver" and "Admin". Restricted
     to `ADMIN` and `SALES_MANAGER`.
   - Customers → PS doesn't name an owner; a customer record is
     day-to-day sales data a rep needs, tied to `assignedRepId`. Write access
     given to `ADMIN`, `SALES_MANAGER`, `SALES_REP`; destructive delete
     restricted to `ADMIN`/`SALES_MANAGER`.
   - All reads (`GET`) in this phase are open to any authenticated internal
     role — nothing here is customer-portal-facing yet (Phase 7).
2. **"Delete" on catalog/price-list resources is a soft delete
   (`isActive=false`), not a physical `DELETE`.** `products.categoryId` is
   `onDelete:'restrict'`, and `quotationItems.productId` /
   `orderItems.productId` are also `restrict` — once a product or price
   list is used anywhere downstream, a hard delete would routinely fail
   mid-demo. Soft delete is idempotent, reversible, and matches the
   `isActive` column already on `products` / `priceLists`.
3. **`customers` has no `isActive` column**, so customer delete *is* a real
   `DELETE`, but only allowed when zero quotations/orders reference the
   customer (checked, not just relied on FK `restrict` as the sole guard).
4. **A category with no configured `category_discount_limits` row is
   treated as unrestricted (100%)** for risk-evaluation purposes, so
   `allowedDiscount = MIN(tierLimit, categoryLimit ?? 100)`. `plan.md` §2.5
   doesn't define the missing-config case, and "no ceiling configured" is
   the safer reading of a config table that's optional per category.
5. **`evaluateQuoteRisk(quotationId)` is built now as an internal service
   only** (`modules/risk`), with no HTTP route. `plan.md` §2.5 frames it as
   "a reusable service", and its only two Phase-3+ callers — quote submit
   (3.4) and negotiation re-approval (Phase 7) — don't exist yet. Wiring it
   to `POST /quotations/:id/submit` happens in Phase 3, without changing
   this service's contract.
6. **A read-only price resolution endpoint (`GET /pricing/resolve`) is
   added under the Price Lists feature.** `plan.md` §2.3's bonus explicitly
   requires "Base Price / Customer Price / Discount / Final Price" to be
   computable for the quotation builder — resolving a customer-tier price
   is core Price-List behavior (a pure config lookup), not quotation
   business logic, so it belongs here rather than being deferred to Phase 3.
7. **Pagination is offset/limit** (`page`, `pageSize`, capped at 100) — fine
   at hackathon/demo data volumes; noted as a scaling caveat, not solved now
   (Rule 5 in `plan.md`: don't over-build infrastructure).
8. **No optimistic-concurrency/version column exists on any table.**
   Field-level admin-config updates are last-write-wins, which is
   acceptable for single-admin config screens. The one place this isn't
   good enough — `approval_rules`, where two concurrent creates could
   produce overlapping bands and silently corrupt the approval chain — is
   handled with an explicit row lock (§5.3 below), not left to chance.

## 3. Shared conventions (apply to every endpoint below unless called out)

| Aspect | Default behavior |
|---|---|
| **Auth** | `authenticate` required on every route in this phase (no public endpoints). |
| **Pagination** | `?page=1&pageSize=20` (max `pageSize=100`); response `meta:{page,pageSize,total,totalPages}`. |
| **Sorting** | `?sortBy=<allowlisted column>&sortDir=asc\|desc`; unknown `sortBy` → `400`. |
| **Filtering** | Documented per endpoint; always translated to indexed `WHERE` clauses. |
| **Validation** | Rejected at the boundary with `400 VALIDATION_FAILED` before any DB call. |
| **Not found** | `404 NOT_FOUND` — looked up by PK, never leaks whether a *conflicting* record exists. |
| **Idempotency (plain create)** | Not idempotent by REST convention; duplicate submissions are caught by a `UNIQUE` constraint → `409`. |
| **Idempotency (upsert-style endpoints)** | True idempotent `PUT`, backed by `INSERT ... ON CONFLICT ... DO UPDATE` — explicitly marked per endpoint. |
| **Rollback** | Any multi-statement write is txn-wrapped; single-statement writes rely on Postgres's own atomicity. |
| **Performance** | List endpoints select only needed columns and hit an existing index for every filter (see per-table `index(...)` calls in schema); no per-row follow-up queries (single joined query instead). |

## 4. API Specifications

### 4.1 Categories (`modules/categories`) — PS §A2, `plan.md` §2.1

| Method & Route | Purpose | Roles |
|---|---|---|
| `GET /categories` | List categories, `?search=name` | any authenticated |
| `GET /categories/:id` | Get one | any authenticated |
| `POST /categories` | Create | `ADMIN` |
| `PATCH /categories/:id` | Rename / edit description | `ADMIN` |
| `DELETE /categories/:id` | Remove an **unused** category | `ADMIN` |

**`DELETE /categories/:id` — the one non-trivial case here.**
- **Transaction boundary:** none needed — Postgres's own `DELETE` statement
  atomicity is sufficient (single-table, single-statement).
- **DB flow:** `DELETE FROM product_categories WHERE id=:id`.
- **Concurrency / rollback:** the `products.category_id` FK is
  `onDelete:'restrict'` and `category_discount_limits.category_id` is
  `onDelete:'cascade'`. A concurrent product-create referencing this
  category and this delete race safely: Postgres serializes them at the
  row-lock level, so either the delete fails with `23503` (product existed
  first) or the product-create's FK check fails (category gone first) —
  never a silent inconsistency.
- **Error mapping:** catch `23503 foreign_key_violation` → `409
  CATEGORY_IN_USE` ("Category has products; deactivate or reassign them
  first."). Deleting cascades any category-level discount ceiling — that's
  intended (a ceiling without a category is meaningless).
- **Success:** `200 { success:true, data:{ deleted:true } }`

All other Category endpoints are the plain single-table CRUD covered by
§3 — create validates `name` (1–100 chars, unique — `23505` → `409
NAME_TAKEN`), update is a partial patch, get/list are indexed reads on
`product_categories_name_unique`.

### 4.2 Products (`modules/products`) — PS §A2, `plan.md` §2.1

| Method & Route | Purpose | Roles |
|---|---|---|
| `GET /products` | List, filters: `categoryId`, `productType`, `isActive`, `search` (name/sku) | any authenticated |
| `GET /products/:id` | Get one, **with variants inlined** | any authenticated |
| `POST /products` | Create product, optionally with initial variants | `ADMIN` |
| `PATCH /products/:id` | Edit general info / toggle `isActive` | `ADMIN` |
| `POST /products/:id/variants` | Add one variant | `ADMIN` |
| `PATCH /products/:id/variants/:variantId` | Edit a variant | `ADMIN` |
| `DELETE /products/:id/variants/:variantId` | Remove a variant | `ADMIN` |
| `DELETE /products/:id` | **Soft delete** (`isActive=false`) | `ADMIN` |

**`POST /products` — the multi-insert case.**
- **Body:** `{ categoryId, sku, name, description, unit, basePrice, estimatedCost, taxRate, productType, variants?: [{attributeName, attributeValue, extraPrice, sku?}] }`
- **Validation:** `categoryId` is a valid UUID that exists (checked in
  service, not just FK — so we return a clean `400`/`404` instead of a raw
  `23503`); `sku` 1–50 chars; `basePrice`, `estimatedCost` ≥ 0;
  `0 ≤ taxRate ≤ 100`; `productType ∈ {ONE_TIME, SERVICE, SUBSCRIPTION}`;
  each variant's `(attributeName, attributeValue)` pair unique within the
  request payload (mirrors the DB's own unique triple, checked early for a
  clean 400 instead of a mid-transaction 409).
- **Idempotency:** not idempotent as a plain `POST`; retried duplicate
  `sku` → `409 SKU_TAKEN` via `products_sku_unique`, no partial product+
  variant row is left behind (see transaction below).
- **Transaction boundary:** `INSERT product` + `INSERT variants[]` in one
  DB transaction — a product is never persisted with only some of its
  requested variants.
- **DB flow:** `SELECT 1 FROM product_categories WHERE id=:categoryId` →
  `INSERT INTO products (...) RETURNING *` → (if variants) batch
  `INSERT INTO product_variants (...) VALUES (...), (...), ...` (single
  multi-row insert, not N round trips).
- **Concurrency:** unique violation on `sku` or on a variant's
  `(product_id, attribute_name, attribute_value)` triple → caught inside
  the transaction, mapped to `409`, full rollback.
- **Rollback:** automatic on any insert failure — no orphaned product
  without its variants, and no variant pointing at a half-created product.
- **Success:** `201 { success:true, data:{ product:{...}, variants:[...] } }`
- **Errors:** `400 VALIDATION_FAILED`, `404 CATEGORY_NOT_FOUND`,
  `409 SKU_TAKEN` / `409 VARIANT_DUPLICATE`, `500`.
- **Performance:** single round trip for all variants via one multi-row
  `INSERT`, not a loop.

**`DELETE /products/:id` (soft delete).**
- Sets `isActive=false, updatedAt=now()`. Idempotent — deleting an already
  inactive product is a no-op `200`, not a `404` (matches PATCH-style
  idempotent-delete semantics, since the row still exists).
- No transaction needed (single-statement `UPDATE`).
- This is why there is **no** `DELETE /products/:id` that removes the row:
  `order_items.product_id` / `quotation_items.product_id` are
  `onDelete:'restrict'`, so a physical delete would start failing the
  moment the product is ever quoted — soft delete sidesteps that per
  assumption 2.

**Variant sub-resource endpoints** (`POST`/`PATCH`/`DELETE
/products/:id/variants[/:variantId]`) are plain single-table CRUD against
`product_variants`, scoped by `productId` in every `WHERE`; duplicate
`(attributeName, attributeValue)` → `409 VARIANT_DUPLICATE` via
`product_variants_product_attr_unique`.

### 4.3 Price Lists (`modules/priceLists`) — PS §A2, `plan.md` §2.3

| Method & Route | Purpose | Roles |
|---|---|---|
| `GET /price-lists` | List | any authenticated |
| `GET /price-lists/:id/items` | List a price list's per-tier prices, filter `productId`/`customerTier` | any authenticated |
| `POST /price-lists` | Create (`name`, `currency`) | `ADMIN` |
| `PATCH /price-lists/:id` | Edit name/currency/`isActive` | `ADMIN` |
| `DELETE /price-lists/:id` | **Soft delete** (`isActive=false`) | `ADMIN` |
| `PUT /price-lists/:id/items` | **Upsert** one product-tier price | `ADMIN` |
| `DELETE /price-lists/:id/items/:itemId` | Remove one tier price | `ADMIN` |
| `GET /pricing/resolve` | Resolve the effective unit price for a customer+product | any authenticated |

**`PUT /price-lists/:id/items` — the idempotent upsert.**
- **Body:** `{ productId, customerTier, unitPrice }`
- **Validation:** `productId` exists and is active; `customerTier ∈
  {BRONZE,SILVER,GOLD}`; `unitPrice ≥ 0`.
- **Idempotency:** genuinely idempotent by design — calling it twice with
  the same body produces the same end state, no duplicate row, via the
  existing unique triple `(priceListId, productId, customerTier)`.
- **Transaction boundary:** none needed — one atomic statement.
- **DB flow:** single statement —
  ```
  INSERT INTO price_list_items (price_list_id, product_id, customer_tier, unit_price)
  VALUES (:id, :productId, :customerTier, :unitPrice)
  ON CONFLICT (price_list_id, product_id, customer_tier)
  DO UPDATE SET unit_price = EXCLUDED.unit_price, updated_at = now()
  RETURNING *
  ```
- **Concurrency:** `ON CONFLICT` makes concurrent upserts of the same
  triple race-free at the database level — no read-then-write gap.
- **Success:** `200 { success:true, data:{ item:{...} } }` (`200` not
  `201` — this is a `PUT`, and it's ambiguous whether it inserted or
  updated; the body being identical either way is the point of an upsert).
- **Errors:** `400`, `404 PRODUCT_NOT_FOUND`, `500`.

**`GET /pricing/resolve?customerId=&productId=`**
- **Purpose:** given a customer (whose `tier` and `priceListId` are known)
  and a product, return `{ basePrice, customerPrice, priceSource,
  currency }` for the quotation builder to consume in Phase 3. This performs
  no discount/margin math — that's the risk/quotation engines' job.
- **DB flow (single query, no N+1):** one query joining
  `customers → priceLists → priceListItems (filtered by productId,
  customer.tier) → products (for basePrice fallback)`.
- **Resolution logic:**
  ```
  IF customer.priceListId is set AND a matching price_list_item exists
     for (that list, productId, customer.tier):
        customerPrice = that item's unitPrice; priceSource = 'PRICE_LIST'
  ELSE:
        customerPrice = product.basePrice; priceSource = 'BASE_PRICE'
  ```
- **Errors:** `404 CUSTOMER_NOT_FOUND`, `404 PRODUCT_NOT_FOUND`.
- **Performance:** one indexed joined `SELECT`; no loop-per-product calls
  (Phase 3's builder should batch this per line, not call it N times per
  product — noted for the Phase-3 design).

All other Price List endpoints are plain CRUD per §3; `price_lists_name_unique`
gives `409 NAME_TAKEN` on duplicate create.

### 4.4 Customers (`modules/customers`) — PS §A2, `plan.md` §2.2

| Method & Route | Purpose | Roles |
|---|---|---|
| `GET /customers` | List, filters: `tier`, `assignedRepId`, `search` (name/email) | any authenticated |
| `GET /customers/:id` | Get one | any authenticated |
| `POST /customers` | Create | `ADMIN`, `SALES_MANAGER`, `SALES_REP` |
| `PATCH /customers/:id` | Edit tier / rep / contact info / price list | `ADMIN`, `SALES_MANAGER`, `SALES_REP` |
| `DELETE /customers/:id` | Remove, only if unreferenced | `ADMIN`, `SALES_MANAGER` |

**`POST /customers`.**
- **Body:** `{ name, email, phone?, tier?, assignedRepId?, priceListId?, billingAddress? }`
- **Validation:** `name` required; `email` valid & unique (case-insensitive,
  checked pre-flight, enforced by `customers_email_lower_unique`); `tier ∈
  {BRONZE,SILVER,GOLD}` (default `BRONZE` matches schema default);
  `assignedRepId`/`priceListId`, if given, must reference existing rows
  (checked in-service for a clean `404` instead of a raw FK error).
- **Idempotency:** not idempotent; duplicate email → `409 EMAIL_TAKEN`.
- **Transaction:** single insert, none needed.

**`DELETE /customers/:id` — the guarded delete.**
- **Transaction boundary:** `SELECT count(*) FROM quotations WHERE
  customer_id=:id` and `SELECT count(*) FROM orders WHERE
  customer_id=:id`, then `DELETE FROM customers WHERE id=:id`, all inside
  one transaction so the check and the delete see a consistent snapshot.
- **Concurrency:** the pre-check closes the common case with a clean
  `409`; the transaction still relies on `quotations.customer_id`
  /`orders.customer_id` being `onDelete:'restrict'` as the final backstop
  in case a quotation is inserted concurrently between the check and the
  delete — caught as `23503` and mapped to the same `409`, so the response
  is identical either way and no race can produce a dangling reference.
- **Rollback:** automatic — a blocked delete rolls the whole transaction
  back; nothing is partially removed.
- **Success:** `200 { success:true, data:{ deleted:true } }`
- **Errors:** `409 CUSTOMER_HAS_ACTIVITY` ("Customer has existing
  quotations or orders and cannot be deleted.").

### 4.5 Governance (`modules/governance`) — PS §A3, `plan.md` §2.4

| Method & Route | Purpose | Roles |
|---|---|---|
| `GET /governance/tier-discount-limits` | List all 3 tiers' max discount % | any authenticated |
| `PUT /governance/tier-discount-limits/:tier` | **Upsert** a tier's max discount % | `ADMIN`, `SALES_MANAGER` |
| `GET /governance/category-discount-limits` | List, joined with category name | any authenticated |
| `PUT /governance/category-discount-limits/:categoryId` | **Upsert** a category's ceiling | `ADMIN`, `SALES_MANAGER` |
| `DELETE /governance/category-discount-limits/:categoryId` | Remove a ceiling (falls back to unrestricted, per assumption 4) | `ADMIN`, `SALES_MANAGER` |
| `GET /governance/approval-rules` | List bands, ordered by `minOveragePct` | any authenticated |
| `POST /governance/approval-rules` | Add a new overage band | `ADMIN`, `SALES_MANAGER` |
| `PATCH /governance/approval-rules/:id` | Edit a band's range/level | `ADMIN`, `SALES_MANAGER` |
| `DELETE /governance/approval-rules/:id` | **Soft delete** (`isActive=false`) | `ADMIN`, `SALES_MANAGER` |

**`PUT /governance/tier-discount-limits/:tier` and
`PUT .../category-discount-limits/:categoryId` — idempotent upserts,**
same `ON CONFLICT ... DO UPDATE` pattern as the price-list item upsert
(§4.3), keyed on `customer_tier_discount_limits_tier_unique` and
`category_discount_limits_category_unique` respectively.
- **Validation:** `0 ≤ maxDiscountPct ≤ 100` (also enforced by the DB
  `check` constraint as a backstop).
- **Errors:** `400`, `404 CATEGORY_NOT_FOUND` (category variant only).

**`POST /governance/approval-rules` — the concurrency-sensitive one.**
- **Purpose:** add a band to the ordered overage→approval-level chain
  (e.g. `[0,10)→NONE`, `[10,20)→MANAGER`, `[20,∞)→MANAGER_FINANCE`).
- **Body:** `{ minOveragePct, maxOveragePct?, requiredLevel }`
- **Validation:** `minOveragePct ≥ 0`; `maxOveragePct` either absent
  (open-ended top band) or `> minOveragePct`; `requiredLevel ∈
  {NONE,MANAGER,MANAGER_FINANCE}`.
- **Idempotency:** not idempotent — each call adds a new band row.
- **Transaction boundary:** the whole read-validate-write sequence is one
  transaction.
- **DB flow:**
  1. `SELECT * FROM approval_rules WHERE is_active=true ORDER BY
     min_overage_pct FOR UPDATE` — row-locks every existing active band.
  2. In application code, confirm `[minOveragePct, maxOveragePct)` doesn't
     overlap any locked existing band.
  3. `INSERT INTO approval_rules (...) RETURNING *`.
- **Concurrency:** the `FOR UPDATE` lock is what makes this safe — without
  it, two concurrent `POST`s each reading the same "gap" would both pass
  the overlap check and insert conflicting bands. With the lock, the
  second transaction blocks until the first commits, then re-validates
  against the now-current (including the first's new row) set.
- **Rollback:** overlap detected → throw inside the transaction → full
  rollback, `409 OVERLAPPING_BAND`.
- **Success:** `201 { success:true, data:{ rule:{...} } }`
- **Errors:** `400 VALIDATION_FAILED`, `409 OVERLAPPING_BAND`, `500`.
- **Performance:** the active-rules set is small (a handful of bands), so
  locking all of them is cheap; this is not a hot-path write endpoint.

`PATCH`/`DELETE` on an existing rule go through the same lock-then-validate
pattern when the range itself changes; a `PATCH` that only flips
`requiredLevel` (not the range) skips the overlap check entirely.

### 4.6 Risk Engine (`modules/risk`) — `plan.md` §2.5 — **internal service, no routes**

```
evaluateQuoteRisk(quotationId) -> RiskEvaluation
```

Not HTTP-exposed this phase (see assumption 5). Documented fully now so
Phase 3's `POST /quotations/:id/submit` and Phase 7's negotiation
re-approval can call it unchanged.

**Inputs read (one batched query, no N+1):**
```
quotation            (customerId, status)
customer             (tier)
quotation_items[]    (productId, quantity, unitPrice, discountPct)
products[]           (categoryId, for each distinct productId on the quote)
customer_tier_discount_limits  (row for customer.tier)
category_discount_limits[]     (rows for every distinct categoryId on the quote)
approval_rules[]     (active bands, ordered by minOveragePct)
```
Fetched as: one query for the quotation + customer (joined), one query for
all quotation items joined to their products (single `IN (...)` join, not
per-line), one query for all relevant category limits (`IN (categoryIds)`),
one query for the tier limit, one query for active approval rules. Five
queries total regardless of line count — not five-times-N.

**Per-line calculation (`plan.md` §2.5 "Minimum logic"):**
```
FOR each quotation_item:
    categoryLimit = categoryLimits[item.product.categoryId]?.maxDiscountPct ?? 100   // assumption 4
    allowedDiscount = MIN(tierLimit.maxDiscountPct, categoryLimit)
    overage = MAX(0, item.discountPct - allowedDiscount)
    lineRisk = overage                              // plan.md: "line risk = max(0, actual - allowed)"
    violation = overage > 0
```

**Blended score (`plan.md` §2.5 "Blended risk"):**
```
lineTotal(item) = item.unitPrice * item.quantity * (1 - item.discountPct/100)
totalRevenue = SUM(lineTotal(item) for all items)

// weighted average of line risks, weighted by each line's share of revenue,
// so a big-ticket line breaking its limit matters more than a token line —
// this is the "aggregate discount pressure" plan.md asks for in one
// transparent, auditable number rather than two separate ad hoc scores.
blendedRiskScore = SUM(lineRisk(item) * lineTotal(item) for all items) / totalRevenue
                    (0 if totalRevenue == 0)
```

**Approval routing:**
```
requiredLevel = 'NONE'
FOR rule in approval_rules (ordered ascending by minOveragePct):
    IF blendedRiskScore >= rule.minOveragePct
       AND (rule.maxOveragePct IS NULL OR blendedRiskScore < rule.maxOveragePct):
        requiredLevel = rule.requiredLevel
        BREAK

approvalChain = requiredLevel == 'NONE' ? []
              : requiredLevel == 'MANAGER' ? ['SALES_MANAGER']
              : ['SALES_MANAGER', 'FINANCE']
```

**Return shape:**
```
{
  quotationId,
  lineViolations: [{ quotationItemId, productId, actualDiscountPct, allowedDiscountPct, overagePct }, ...],
  customerTier, tierLimitPct,
  categoryViolations: [{ categoryId, categoryName, limitPct }, ...],   // categories with >=1 violating line
  blendedRiskScore,
  requiredApprovalLevel,     // NONE | MANAGER | MANAGER_FINANCE
  approvalChain              // e.g. ['SALES_MANAGER','FINANCE']
}
```

- **Side effects:** **none.** This function is a pure read + calculation —
  it does not write `blendedRiskScore`/`requiredApprovalLevel` back onto
  the `quotations` row or create an `approval_requests` row. Persisting the
  result and creating the approval request is Phase 3's job (3.4 "Automatic
  Approval Trigger"), which calls this function as one step inside its own
  transaction. Keeping this function side-effect-free is what makes it
  safely reusable from both the initial submit flow and the later
  negotiation re-approval flow without duplicating persistence logic.
- **Concurrency:** none to manage here — no writes.
- **Performance:** fixed number of queries (5) regardless of line count;
  all filtered by existing indexes (`quotation_items_quotation_id_idx`,
  `category_discount_limits_category_unique`,
  `customer_tier_discount_limits_tier_unique`,
  `approval_rules_min_overage_idx`).

## 5. Pseudocode Files

**File: `server/src/common/pagination.util.js`**
```
MODULE pagination.util

FUNCTION parseListQuery(query, { allowedSortColumns, defaultSort }):
    page = MAX(1, int(query.page) OR 1)
    pageSize = CLAMP(int(query.pageSize) OR 20, 1, 100)

    tierLimit = (await repo.getTierLimit(customerTier))?.maxDiscountPct OR 0
    categoryIds = uniq(lines.map(l => l.categoryId))
    categoryLimitsById = keyBy(await repo.getCategoryLimits(categoryIds), 'categoryId')
    approvalRules = await repo.getActiveApprovalRules()

    lineViolations = []
    weightedRiskSum = 0
    totalRevenue = 0

    FOR l IN lines:
        categoryLimit = categoryLimitsById[l.categoryId]?.maxDiscountPct ?? 100   // assumption 4
        allowedDiscount = MIN(tierLimit, categoryLimit)
        overage = MAX(0, l.item.discountPct - allowedDiscount)
        lineTotal = l.item.unitPrice * l.item.quantity * (1 - l.item.discountPct/100)
        totalRevenue += lineTotal
        weightedRiskSum += overage * lineTotal
        IF overage > 0:
            lineViolations.push({ quotationItemId: l.item.id, productId: l.item.productId,
                                   actualDiscountPct: l.item.discountPct, allowedDiscountPct: allowedDiscount,
                                   overagePct: overage })

    blendedRiskScore = totalRevenue > 0 ? (weightedRiskSum / totalRevenue) : 0

    requiredLevel = 'NONE'
    FOR rule IN approvalRules:
        IF blendedRiskScore >= rule.minOveragePct AND (rule.maxOveragePct == null OR blendedRiskScore < rule.maxOveragePct):
            requiredLevel = rule.requiredLevel
            BREAK

    approvalChain = requiredLevel=='NONE' ? [] : requiredLevel=='MANAGER' ? ['SALES_MANAGER'] : ['SALES_MANAGER','FINANCE']

    categoryViolations = uniqBy(lineViolations.map(v => lines.find(l=>l.item.id==v.quotationItemId))
                                  .map(l => ({ categoryId:l.categoryId, categoryName:l.categoryName,
                                               limitPct: categoryLimitsById[l.categoryId]?.maxDiscountPct ?? 100 })), 'categoryId')

    RETURN { quotationId, lineViolations, customerTier, tierLimitPct: tierLimit,
             categoryViolations, blendedRiskScore, requiredApprovalLevel: requiredLevel, approvalChain }
    // NOTE: pure function — no writes to `quotations` or `approval_requests` here (see §4.6)
```
