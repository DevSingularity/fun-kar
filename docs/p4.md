# DealFlow360 — Phase 4 API Design
## Upsell/Cross-Sell + Approval UI (`plan.md` Hour 3.5–4.5)

Builds on Phase 3 (`modules/quotations`, `modules/approval` writer, `risk.evaluateQuoteRisk`/`resolveAllowedDiscount`). Scope is strictly §4.1–4.2 of `plan.md`: the upsell/cross-sell recommendation engine + "Add to Quote" action, and the Approval Dashboard's Approve/Reject/Return actions with audit trail and explainability. Fulfillment (Phase 5), billing (Phase 6), and the customer portal (Phase 7) are **not** built here.

---

## 1. Assumptions carried into this phase

1. **`upsell_rules` gets Admin CRUD now, not in Phase 2.** `plan.md` places "Upsell/Cross-Sell Engine" entirely in §4.1 (Phase 4) — it is never listed in Phase 2's §2.1–2.5 scope, and Phase 1's seed data (§4) only pre-populates rows for the demo. Since nothing else in the plan ever gives this table a writer, and PS §A6 explicitly describes it as Admin backend configuration, Phase 4 adds a small `ADMIN`-only CRUD surface alongside the recommendation engine that reads it. This is additive, not a Phase 2 scope violation — Phase 2 is unchanged.
2. **"Dismiss" is a client-only interaction.** `plan.md` §4.1 lists it as a panel button, but nothing in the schema (`quotation_items`, `upsell_rules`) has anywhere to persist a per-quotation dismissal, and no later phase reads one. Persisting dismissals would be inventing a requirement; the panel simply drops the suggestion from its local list until the cart changes and suggestions are re-fetched.
3. **A suggestion's "margin delta" is computed as an in-memory simulation, not a persisted comparison.** `plan.md` §3.3 says "update immediately when ... an upsell item is added" — so the panel needs to preview the *quote-level* margin change before commit. `quotations.calc.computeQuotationTotals` (Phase 3, pure) is reused to compute `currentTotals` vs `totals-if-this-line-were-appended`, with no DB write until "Add to Quote" is actually clicked.
4. **The per-rule `minMarginPct` filter is evaluated against the recommended product's own unit margin** (`(customerPrice − estimatedCost) / customerPrice × 100`), not the blended quote margin. `plan.md` §A6 frames it as a property of the *product suggestion* ("set minimum margin thresholds so only healthy margin suggestions surface"), independent of whatever else is already in the cart.
5. **"Add to Quote" is a new endpoint, not a parameter bolted onto Phase 3's `POST /quotations/:id/items`.** Sourcing a line from a specific `upsell_rules` row is a distinct, validated action (the rule must exist, be active, and recommend a product not already in the cart) — modeling it as its own route keeps Phase 3's generic item-add endpoint free of upsell-specific validation, while internally it reuses Phase 3's same transactional insert-and-recompute logic (extracted into a shared internal function, detailed in §5.4).
6. **Approval chain progress is derived, never stored as a separate "current step" column.** `approval_requests.requiredLevel` (frozen at submit time) plus the `approval_actions` history are sufficient to derive whether a `MANAGER_FINANCE` request is currently awaiting the Manager or Finance step — adding a redundant mutable column would risk drifting out of sync with the action log, which is the audit-trail source of truth.
7. **`ADMIN` may act at either approval step (override), `SALES_MANAGER` only at the Manager step, `FINANCE` only at the Finance step.** The Problem Statement's role table doesn't explicitly grant Admin this override, but §3 gives Admin platform-wide configuration/oversight authority and a hackathon demo needs an escape hatch when a Manager/Finance account isn't available — this is called out explicitly as a judgment call, not read literally from the PS.
8. **Approve/Reject/Return are *not* idempotent-replay like Phase 3's `submit`.** A retried `submit` safely returns the already-computed state because it's a system-triggered calculation with no attributable human judgment. An approval decision is a specific person's accountable action recorded in the audit trail — silently absorbing a second identical call would misrepresent who decided what, and could mask a genuine double-submission bug. A retry against an already-resolved request instead returns `409 ALREADY_RESOLVED` with the current state in the error body, so the client can safely refetch and reconcile without ever recording two decisions.
9. **The live "why approval is required" breakdown re-runs `risk.evaluateQuoteRisk` at read time** rather than only showing the frozen `blendedRiskScore`/`requiredApprovalLevel` snapshot on the quotation. This satisfies `plan.md` §2.5's bonus (line-by-line explanation) without duplicating that computation in the approval module. If governance config changed since submit, the live breakdown and the frozen routing decision can disagree — the UI shows both; **the frozen `requiredApprovalLevel` is what the approver is actually acting on**, never silently replaced by a fresher recomputation mid-flow.
10. **The margin-impact bonus (`plan.md` §4.2) compares "margin at the actual requested discounts" vs. "margin if every line were capped at its own `allowedDiscountPct`"** — a pure, in-memory re-run of `quotations.calc.computeQuotationTotals` over the stored line snapshots with `discountPct` swapped for `allowedDiscountPct` where the line is in violation. No new persisted field; this is response-shaping only.
11. **Approval-request list visibility is role-scoped by *current required step*, not by requester identity** — a `SALES_MANAGER` only ever sees requests currently awaiting the Manager step; `FINANCE` only sees ones currently awaiting the Finance step; `ADMIN` sees everything. This mirrors Phase 3's ownership-scoping pattern but keyed on the approval chain rather than `salesRepId`.

### 4.1 `GET /quotations/:id/upsell-suggestions` — the recommendation engine

- **Purpose:** for every product currently in the cart, find `upsell_rules` whose `triggerProductId` matches, exclude products already on the quote, price + margin-filter + rank the rest.
- **DB flow (single query, no N+1):** one query joining `quotation_items (this quotation) → upsell_rules (on triggerProductId) → products (recommended) → product_categories`, `WHERE recommendedProductId NOT IN (this quotation's product ids) AND upsell_rules.isActive`.
- **Per-candidate computation (in application code, all inputs already fetched in the one query above — no per-candidate DB round trip):**
  1. `priceLists.service.resolve({ customerId, productId: recommendedProductId })` — **batched**: resolve all distinct candidate product prices in one pass by reusing `priceLists.repository`'s joined-query shape rather than calling `.resolve()` once per candidate (Phase 2's own performance note for this exact pattern); exposed as `priceListsService.resolveMany({ customerId, productIds })`, a thin batching wrapper the Price Lists module adds now (returns a map, same underlying single joined `SELECT ... WHERE productId IN (...)`).
  2. `unitMarginPct = (customerPrice − recommendedProduct.estimatedCost) / customerPrice × 100`; drop the candidate if `unitMarginPct < rule.minMarginPct`.
  3. `marginDelta` (currency amount) — simulate appending one unit of this product (qty 1, discount 0%) to the existing line snapshots via `quotations.calc.computeQuotationTotals`, and diff `marginAmount` before/after.
  4. `reason` string, honestly labeled: `"<coPurchaseScore>% of similar <triggerProduct> quotes include this item"` sourced from the seeded/derived `coPurchaseScore` column (assumption carried from `plan.md` §4.1 bonus: "label the source honestly as historical purchase data").
- **Ranking:** sort by `(isPromoted DESC, coPurchaseScore DESC)`; ties broken by `marginDelta DESC`. Cap at `?limit` (default 5, max 10).
- **Success:** `200 { success:true, data:{ suggestions:[{ ruleId, productId, productName, sku, unitPrice, currency, marginDelta, isPromoted, reason }] } }`.
- **Errors:** `403 FORBIDDEN` (not owner), `404 NOT_FOUND` (quotation).
- **Performance:** 2 queries total (candidate join + batched price resolution) regardless of cart size or candidate count; the margin-delta simulation is pure in-memory arithmetic over already-loaded line snapshots.

### 4.2 `POST /quotations/:id/items/from-upsell/:ruleId` — Add to Quote

- **Purpose:** commit exactly one suggested line, defaulting `quantity=1`, `discountPct=0`, and stamping `isUpsell=true`, `sourceUpsellRuleId=ruleId` — the margin/total recompute is the same Phase-3 transaction, just a different entry point.
- **Validation (service-level, not just shape):** rule exists and `isActive`; rule's `recommendedProductId` is not already a line on this quotation (`409 ALREADY_IN_QUOTE` — re-clicking "Add" after it's already there is a no-op-with-error, not a silent duplicate line); quotation is the rule's actual context (rule itself has no `quotationId` — validity is just "exists and active", the cart-membership check is what's quotation-specific).
- **Idempotency:** the "already in quote" check makes a retried click a safe `409`, never a duplicate line — same posture as every other plain create in this codebase, made explicit here because the button is naturally double-clickable.
- **Transaction boundary / DB flow:** identical to Phase 3 `addItem` (lock quotation → verify `DRAFT` → resolve product/price/allowed-discount → insert → recompute aggregates), reached via the shared `insertItemTx()` extracted in `quotations.service.js` (see §5.4) with `isUpsell=true` and `sourceUpsellRuleId` passed through.
- **Success:** `201 { success:true, data:{ item, quotation:{ subtotal, discountTotal, taxTotal, grandTotal, estimatedMarginPct } } }` — identical response shape to Phase 3's `addItem`, so the builder UI's margin indicator updates the same way either path is used.
- **Errors:** `403 FORBIDDEN`, `404 NOT_FOUND` (quotation/rule/product), `409 INVALID_STATE` (not `DRAFT`), `409 ALREADY_IN_QUOTE`, `500`.

### 4.3 `GET /approval-requests` — the dashboard list

- **Purpose:** each role sees only what it can currently act on.
- **DB flow (single query, no N+1):** `approval_requests` joined to `quotations`→`customers` for the summary columns, plus a correlated boolean subquery `managerApproved = EXISTS (SELECT 1 FROM approval_actions WHERE approval_request_id = approval_requests.id AND level='MANAGER' AND action='APPROVED')`. Role-scoping is then a `WHERE` clause over that same query — no second pass, no per-row follow-up:
  ```
  SALES_MANAGER: status='PENDING' AND (requiredLevel='MANAGER' OR (requiredLevel='MANAGER_FINANCE' AND NOT managerApproved))
  FINANCE:       status='PENDING' AND requiredLevel='MANAGER_FINANCE' AND managerApproved
  ADMIN:         no additional restriction (optional ?status= filter still applies)
  ```
- **Success:** `200 { success:true, data:{ items:[{ id, quotationId, quoteNumber, customerName, grandTotal, blendedRiskScore, requiredLevel, currentStep, requestedAt }], meta } }`.

### 4.4 `POST /approval-requests/:id/approve|reject|return` — the decision actions

- **Purpose:** record one accountable decision per call, advance or resolve the request, and cascade the quotation's status.
- **Body:** `approve`: `{ reason? }`. `reject`/`return`: `{ reason }` (required, 1–2000 chars).
- **Auth:** role must match the request's **current required step** (§1 assumption 6/7), else `403 FORBIDDEN` — checked *after* confirming the request is still `PENDING`, so a resolved request never leaks its would-have-been authorization outcome.
- **Idempotency:** see assumption 8 — a second call against an already-resolved request is `409 ALREADY_RESOLVED`, never a silent replay.
- **Transaction boundary:** one transaction: lock `approval_requests` row → verify `PENDING` → verify actor's step match → insert `approval_actions` → decide next state (`stay PENDING at next step` / `APPROVED` / `REJECTED` / `RETURNED`) → update `approval_requests.status` (+`resolvedAt` if terminal) → update `quotations.status` accordingly → insert one `audit_logs` row (`entityType='QUOTATION'`).
- **State transition table:**

  | Action | Chain state before | `approval_requests.status` after | `quotations.status` after |
  |---|---|---|---|
  | Approve | `MANAGER` required, or `MANAGER_FINANCE` at Manager step | `PENDING` (unchanged — Finance step still owed) | `PENDING_APPROVAL` (unchanged) |
  | Approve | `MANAGER_FINANCE` at Finance step (final) | `APPROVED` | `APPROVED` |
  | Reject | any step | `REJECTED` | `REJECTED` (terminal) |
  | Return | any step | `RETURNED` | `DRAFT` (rep can edit + resubmit; a fresh `approval_requests` row is created on the next `submit`, since this one is no longer `PENDING`) |

- **Concurrency:** the row lock serializes a double-click or a Manager/Admin race on the same request; the second caller reads the already-updated `status` inside the same transaction attempt and is turned into a clean `409` rather than a corrupted double-action.
- **Rollback:** any failure rolls back the `approval_actions` insert, the `approval_requests`/`quotations` status updates, and the audit log together — never a partial state.
- **Success:** `200 { success:true, data:{ approvalRequest, quotation } }`.
- **Errors:** `400 VALIDATION_FAILED` (missing reason on reject/return), `403 FORBIDDEN`, `404 NOT_FOUND`, `409 ALREADY_RESOLVED`, `500`.

### 4.5 `GET /approval-requests/:id` — explainability detail

- **Purpose:** the `plan.md` §2.5/§4.2 bonus screen — "why approval is required" and "margin impact."
- **DB/service flow:** `repo.findByIdJoined(id)` (quotation + customer + requester) → `repo.findActions(id)` (history, joined to `users` for actor name) → `risk.service.evaluateQuoteRisk(quotationId)` (live, for the line/category violation breakdown — assumption 9) → `quotations.calc`-based margin-impact simulation (assumption 10).
- **Success:** `200 { success:true, data:{ approvalRequest, quotation, actions, riskEvaluation, marginImpact:{ marginAtRequestedPct, marginAtAllowedPct, impactPct } } }`.
- **Errors:** `403 FORBIDDEN`, `404 NOT_FOUND`.

    errors = []
    IF NOT isUUID(body.triggerProductId): errors.push('triggerProductId is required.')
    IF NOT isUUID(body.recommendedProductId): errors.push('recommendedProductId is required.')

        triggerProductId: body.triggerProductId, recommendedProductId: body.recommendedProductId,
        minMarginPct, coPurchaseScore, isPromoted: !!body.isPromoted

FUNCTION insertRule(data):
    TRY: RETURN db.insert(upsellRules).values(data).returning().first()
    CATCH e: IF e.code=='23505': THROW ConflictError('RULE_EXISTS','A rule for this product pair already exists.')
             THROW e

FUNCTION list({ triggerProductId, isActive, offset, limit }):
    conditions = []
    IF triggerProductId: conditions.push(eq(upsellRules.triggerProductId, triggerProductId))
    IF isActive != undefined: conditions.push(eq(upsellRules.isActive, isActive))
    rows = db.select().from(upsellRules).where(and(...conditions)).limit(limit).offset(offset)
    total = db.select({count:sql`count(*)`}).from(upsellRules).where(and(...conditions)).first()
    RETURN { rows, total }

FUNCTION findById(id) -> db.select().from(upsellRules).where(eq(upsellRules.id,id)).first()
FUNCTION findByIdActive(id) -> db.select().from(upsellRules).where(and(eq(upsellRules.id,id), eq(upsellRules.isActive,true))).first()
FUNCTION update(id, data) -> db.update(upsellRules).set(data).where(eq(upsellRules.id,id)).returning().first()
FUNCTION softDelete(id) -> db.update(upsellRules).set({isActive:false}).where(eq(upsellRules.id,id)).returning().first()

// --- Recommendation-engine reads ---

FUNCTION findCandidatesForQuotation(quotationId):
    // single joined query: every active rule triggered by a product already in the cart,
    // excluding rules whose recommendation is already a line on this quotation
    inCart = db.select({productId: quotationItems.productId}).from(quotationItems)
                .where(eq(quotationItems.quotationId, quotationId))   // subquery, not a loop

    RETURN db.select({
        rule: upsellRules,
        recommendedProduct: products,
        categoryName: productCategories.name
    })
    .from(upsellRules)
    .innerJoin(quotationItems, and(
        eq(quotationItems.quotationId, quotationId),
        eq(quotationItems.productId, upsellRules.triggerProductId)
    ))
    .innerJoin(products, eq(products.id, upsellRules.recommendedProductId))
    .innerJoin(productCategories, eq(productCategories.id, products.categoryId))
    .where(and(
        eq(upsellRules.isActive, true),
        notInArray(upsellRules.recommendedProductId, inCart)
    ))
```

IMPORT * as repo FROM './intelligence.repository.js'
IMPORT * as quotationsService FROM '../quotations/quotations.service.js'
IMPORT * as priceListsService FROM '../priceLists/priceLists.service.js'
IMPORT * as calc FROM '../quotations/quotations.calc.js'

// --- Admin config CRUD (thin, same shape as Phase 2's Categories module) ---

FUNCTION getById(id):

    IF NOT row: THROW NotFoundError('Upsell rule')
    RETURN row
FUNCTION create(payload):
    IF NOT await productExists(payload.triggerProductId): THROW NotFoundError('Trigger product')
    IF NOT await productExists(payload.recommendedProductId): THROW NotFoundError('Recommended product')
    RETURN repo.insertRule(payload)
FUNCTION update(id, payload):
    await getById(id)
    RETURN repo.update(id, { ...payload })
FUNCTION remove(id):
    await getById(id)
    RETURN repo.softDelete(id)     // idempotent, same pattern as Phase 2 catalog soft-deletes

// --- Recommendation engine ---

FUNCTION suggestForQuotation(quotationId, auth, limit=5):
    detail = await quotationsService.getDetail(quotationId, auth)   // reuses Phase-3 ownership check + 404
    candidates = await repo.findCandidatesForQuotation(quotationId)
    IF candidates.length == 0: RETURN { suggestions: [] }

    productIds = uniq(candidates.map(c => c.recommendedProduct.id))
    priceByProduct = await priceListsService.resolveMany({ customerId: detail.quotation.customerId, productIds })

    currentTotals = calc.computeQuotationTotals(detail.items)

    scored = []
    FOR c IN candidates:
        price = priceByProduct[c.recommendedProduct.id]
        unitMarginPct = price.customerPrice > 0
            ? round2((price.customerPrice - c.recommendedProduct.estimatedCost) / price.customerPrice * 100)
            : 0
        IF unitMarginPct < c.rule.minMarginPct: CONTINUE   // margin-eligibility filter, plan.md §4.1

        hypotheticalLine = calc.computeLineTotals({
            unitPrice: price.customerPrice, quantity: 1, discountPct: 0,
            taxRatePct: c.recommendedProduct.taxRate, estimatedCostPerUnit: c.recommendedProduct.estimatedCost
        })
        hypotheticalTotals = calc.computeQuotationTotals([...detail.items, { ...hypotheticalLine, unitPrice: price.customerPrice, quantity: 1 }])
        marginDelta = round2(hypotheticalTotals.marginAmount - currentTotals.marginAmount)

        scored.push({
            ruleId: c.rule.id, productId: c.recommendedProduct.id, productName: c.recommendedProduct.name,
            sku: c.recommendedProduct.sku, unitPrice: price.customerPrice, currency: price.currency,
            marginDelta, isPromoted: c.rule.isPromoted,
            reason: `${c.rule.coPurchaseScore}% co-purchase strength from historical order data`
        })

    scored.sort(byDesc('isPromoted', 'coPurchaseScoreImplied', 'marginDelta'))   // isPromoted first, then rule.coPurchaseScore, then marginDelta
    RETURN { suggestions: scored.slice(0, limit) }

FUNCTION addSuggestionToQuote(quotationId, ruleId, auth):
    rule = await repo.findByIdActive(ruleId)
    IF NOT rule: THROW NotFoundError('Upsell rule')
    RETURN quotationsService.addUpsellItem(quotationId, {
        productId: rule.recommendedProductId, quantity: 1, discountPct: 0, sourceUpsellRuleId: rule.id
    }, auth)
    // ALREADY_IN_QUOTE / INVALID_STATE / NOT_FOUND surfaced from quotations.service, not duplicated here

### 5.2 Quotations module addition (extends Phase 3's `quotations.service.js`)

**File: `server/src/modules/quotations/quotations.service.js`** *(diff — refactor + one new export)*
```
// Phase 3's addItem() body is refactored into a shared internal function so the
// upsell entry point (addUpsellItem) reuses the exact same lock/validate/insert/
// recompute transaction instead of a parallel copy.

FUNCTION insertItemTx(quotationId, { productId, quantity, discountPct, isUpsell, sourceUpsellRuleId }, auth):
    RETURN db.transaction(async (tx) => {
        quotation = await getOwnedDraft(tx, quotationId, auth)

        product = await productsService.getById(productId)
        IF NOT product.isActive: THROW ConflictError('PRODUCT_INACTIVE', 'This product is no longer sellable.')

        IF isUpsell:
            alreadyInCart = await repo.findItemByProduct(tx, quotationId, productId)
            IF alreadyInCart: THROW ConflictError('ALREADY_IN_QUOTE', 'This product is already a line on the quotation.')

        price = await priceListsService.resolve({ customerId: quotation.customerId, productId: product.id })
        allowedDiscountPct = await riskService.resolveAllowedDiscount(quotation.customerTier, product.categoryId)

        lineCalc = calc.computeLineTotals({
            unitPrice: price.customerPrice, quantity, discountPct,
            taxRatePct: product.taxRate, estimatedCostPerUnit: product.estimatedCost
        })

        item = await repo.insertItem(tx, {
            quotationId, productId: product.id, quantity, unitPrice: price.customerPrice,
            allowedDiscountPct, discountPct, isUpsell: !!isUpsell, sourceUpsellRuleId: sourceUpsellRuleId OR null,
            ...lineCalc
        })
        updatedQuotation = await recomputeAndPersistTotals(tx, quotationId)
        RETURN { item, quotation: updatedQuotation }
    })

FUNCTION decide(id, action, payload, auth):
    // action IN {'APPROVED','REJECTED','RETURNED'}
    RETURN db.transaction(async (tx) => {
        request = await repo.lockById(tx, id)
        IF NOT request: THROW NotFoundError('Approval request')
        IF request.status != 'PENDING':
            THROW ConflictError('ALREADY_RESOLVED', `This request was already ${lower(request.status)}.`)

        priorActions = await repo.findActions(id)       // read inside the same lock — consistent snapshot
        step = currentStep(request.requiredLevel, priorActions)
        assertActorCanAct(auth, step)

        await repo.insertAction(tx, {
            approvalRequestId: id, actorId: auth.userId, level: step, action, reason: payload.reason
        })

        isFinalStep = action != 'APPROVED' ? true
            : (request.requiredLevel == 'MANAGER' OR step == 'FINANCE')

        newRequestStatus = action == 'APPROVED'
            ? (isFinalStep ? 'APPROVED' : 'PENDING')
            : action                                     // 'REJECTED' or 'RETURNED'

        updatedRequest = newRequestStatus == request.status
            ? request
            : await repo.resolveRequest(tx, id, newRequestStatus)   // only touches resolvedAt on terminal states

        newQuotationStatus = newRequestStatus == 'APPROVED' ? 'APPROVED'
            : newRequestStatus == 'REJECTED' ? 'REJECTED'
            : newRequestStatus == 'RETURNED' ? 'DRAFT'
            : 'PENDING_APPROVAL'                          // unchanged — still awaiting Finance

        updatedQuotation = await quotationsRepo.applySubmitResult(tx, request.quotationId, {
            status: newQuotationStatus,
            blendedRiskScore: request.blendedRiskScore, requiredApprovalLevel: request.requiredLevel
        })

        await repo.insertAuditLog(tx, {
            actorId: auth.userId, entityType:'QUOTATION', entityId: request.quotationId,
            action: `APPROVAL_${action}`, reason: payload.reason,
            oldValue: { status: request.status == 'PENDING' ? 'PENDING_APPROVAL' : request.status },
            newValue: { status: newQuotationStatus, level: step }
        })

        RETURN { approvalRequest: updatedRequest, quotation: updatedQuotation }
    })

FUNCTION approve(id, payload, auth) -> decide(id, 'APPROVED', payload, auth)
FUNCTION reject(id, payload, auth)  -> decide(id, 'REJECTED', payload, auth)
FUNCTION returnForRevision(id, payload, auth) -> decide(id, 'RETURNED', payload, auth)
