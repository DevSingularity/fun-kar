# DealFlow360 — Phase 9 API Design
## Hardening + Demo Polish (`plan.md` §9, Hour 7.5–8)

This phase is explicitly **not** a feature phase — `plan.md`'s own heading is *"Stop adding risky features. Make the existing system reliable and impressive."* Per Rule 1–5 (`plan.md`, "8-Hour Execution Rules") and the "If Time Runs Out" priority list (features 1–13 must already exist before this phase starts), Phase 9 introduces **zero new tables and zero new business-logic endpoints**. Its only deliverables are: (a) a cross-cutting audit of every endpoint built in Phases 1–8 against the eleven "Every API must be..." requirements from the top of this whole exercise, (b) concrete pseudocode patches for the gaps that audit finds, (c) a seed-data completion pass so the demo scenario `plan.md` §4 describes is actually buildable end-to-end, and (d) an automated smoke-test script that walks `plan.md` §9.1's ten-step Critical Validation list and §9's own "Quick Test Flow (Login to Payment)" eight-step list. Nothing here modifies the request/response shape of any endpoint from Phases 1–8.

## 1. Assumptions carried into this phase

1. **"Hardening" means closing gaps against the standing cross-phase requirements, not re-litigating design decisions already made.** Every "Every API must be..." property (idempotent, transaction-safe, race-safe, paginated, N+1-free, consistent envelope, timeout/retry-aware) was supposed to be satisfied *at the time each phase was written*. This phase's job is to verify that against what actually exists in the codebase today and patch the deltas — it does not re-open settled modeling assumptions from Phases 1–8 (e.g. it does not revisit Phase 5's stock-decrement strategy or Phase 8's advisory-lock refresh pattern; those are correct as designed).
2. **Two concrete regressions were found by inspecting the current server tree** (`server/src/middlewares/`, `server/src/app.js`) rather than assumed: (a) `rateLimiter.middleware.js` exports `authLimiter` and `apiLimiter`, but **neither is mounted anywhere** — `app.js` and `routes/index.js` never reference them, so brute-force login attempts and API hammering are currently unthrottled despite the middleware existing. (b) There are **two error-handling middlewares** on disk (`middlewares/errorHandler.middleware.js`, wired into `app.js` and Postgres-error-aware per code `23505`/`23503`; and a second, unused `middlewares/error.middleware.js` that predates it, with a plain `err.statusCode || 500` shape and no Postgres-error translation). Only the first is actually mounted, but the second is dead code that risks being wired in by mistake during a rushed final hour. Both are fixed in §4 below as a house-keeping, zero-risk change (Rule 5 — this is deletion/wiring, not new logic).
3. **Order creation (`POST /quotations/:quotationId/orders`, Phase 5 §4.1) is re-specified here to be genuinely idempotent, not merely unique-constrained.** Phase 5's own spec relies on `orders_quotation_id_unique` to prevent a second order for the same quotation, but a unique-index violation surfaces to the caller as `409 CONFLICT` on a *retry* of the exact same request — which is not idempotent by this project's own definition (an idempotent endpoint returns the **same success result** on retry, not an error). This phase changes that one code path to a "find-existing-or-create" pattern: on unique-violation, re-select and return the existing order with `200` instead of propagating the DB error as `409`. This is the single functional (not merely cosmetic) fix in this phase, and it is scoped to exactly the one line of behavior Phase 5 under-specified — no other Phase 5 logic changes.
4. **The demo seed script (`server/src/db/seed.js`) currently only covers Phase 1–2 master data** (users, categories, products, price lists, tier/category discount limits, approval rules) — inspection shows it has no `warehouses`/`warehouse_stock` rows, no `subscription_plans`, and no `upsell_rules`, i.e. it predates the Phase 5–8 schema additions. Since `plan.md` §4's "Bonus" demo scenario (*Gold customer + Laptop + Setup Service + Cloud Subscription + service discount over threshold + Laptop stock split across two warehouses*) is unbuildable without that master data existing, completing the seed script is this phase's second concrete deliverable — not a new feature, but finishing an existing one so the demo (§9's entire purpose) is possible at all.
5. **The seed script seeds *master data* for the scenario, not a pre-built quotation.** `plan.md`'s Quick Test Flow is explicitly a *live* walkthrough ("Create a quotation and add a product line with a discount that is higher than what is normally allowed") — pre-seeding a finished quotation would let the demo skip the very steps §9.1 exists to validate. The seed script's job is only to guarantee the *preconditions* are true: a `GOLD` customer exists; `Laptop`/`Setup Service`/`Cloud Infrastructure` products exist in categories with the right discount ceilings; two active warehouses exist with `Laptop` stock split so that no single warehouse can cover a demo-sized order (forcing the auto-split the rep will demo live); an active monthly/quarterly subscription plan exists for the Cloud Infrastructure product.
6. **The smoke-test script (`scripts/test-critical-flow.js`) is additive, following the existing convention already established in this repo's own `scripts/test-e2e-deep.js`** (a plain `assert(condition, message)` counter, an `HTTP fetch`-based `request()` helper hitting a locally spun-up `app.js` instance, no external test framework). It is scoped to walk exactly `plan.md` §9.1's ten named tests end-to-end across every phase (1 through 8), which the existing `test-e2e-deep.js`/`test-phase{2,3,4}.js` scripts do not do individually — each of those covers one phase in isolation. This script is the first one that exercises the **full chain** (login → config → quote → discount → approval → upsell → warehouse split → hybrid billing → negotiation → confirmation → dashboard) as `plan.md` itself frames the "Definition of a Stable MVP."
7. **No new environment variables, no new dependencies, no new tables.** Every fix in this phase is either (a) wiring an already-written, already-tested piece of middleware into `app.js`, (b) deleting genuinely dead code, (c) changing one error-handling branch in one service function to satisfy this project's own idempotency definition, (d) adding rows to a seed script, or (e) adding a test script. This keeps the phase inside Rule 5's "don't build infrastructure you don't need" for the final half-hour.

## 4. Pseudocode implementation

### 4.1 Idempotent order creation (patches `fulfillment.service.js`, Phase 5 §4.1)

```
MODULE fulfillment.service   (patch — only createOrderFromQuotation changes)

ASYNC FUNCTION createOrderFromQuotation(quotationId, actor):
    db = getDb()
    TRY:
        RETURN AWAIT db.transaction(ASYNC (tx) => {
            quotation = AWAIT repo.findQuotationForUpdate(tx, quotationId)
            IF NOT quotation: THROW NotFoundError('Quotation not found')
            enforceOwnershipOrManagementRole(actor, quotation)   // unchanged from Phase 5
            IF quotation.status != 'APPROVED': THROW ConflictError('Quotation is not APPROVED')

            order = AWAIT repo.insertOrderFromQuotation(tx, quotation)     // may throw 23505 on unique_quotation_id
            items = AWAIT repo.insertOrderItemsFromQuotationItems(tx, order.id, quotation.id)
            allocationResult = AWAIT allocateOrder(order.id, tx)           // unchanged first-allocation-pass call
            RETURN { order, items, allocationResult, alreadyExisted: false }
        })
    CATCH err:
        // NEW — idempotency fix (assumption 3): a retry of the same request hits the
        // orders_quotation_id_unique constraint; treat that as success, not failure.
        IF err.code == '23505' AND err.constraint == 'orders_quotation_id_unique':
            existingOrder = AWAIT repo.findOrderByQuotationId(getDb(), quotationId)
            existingItems = AWAIT repo.findOrderItems(getDb(), existingOrder.id)
            existingAllocation = AWAIT repo.getAllocationSummary(getDb(), existingOrder.id)
            RETURN { order: existingOrder, items: existingItems, allocationResult: existingAllocation, alreadyExisted: true }
        THROW err   // any other error still propagates to errorHandler as before

EXPORT { createOrderFromQuotation, ...rest unchanged from Phase 5 }
```

```
MODULE fulfillment.controller   (patch — only createFromQuotationController changes)

createFromQuotationController = asyncHandler(ASYNC (req, res) => {
    result = AWAIT service.createOrderFromQuotation(req.params.quotationId, req.auth)
    // NEW — 200 on replay (already existed) vs 201 on first creation, per this project's
    // own status-code convention for idempotent-create endpoints
    statusCode = result.alreadyExisted ? 200 : 201
    successResponse(res, result, statusCode)
})
```

No route, validator, or repository *shape* changes — `repo.findOrderByQuotationId` and `repo.findOrderItems` already exist (used by `GET /orders/:id`); this only calls them from a new branch.

### 4.4 Seed-script completion (patches `db/seed.js`)

```
MODULE db.seed   (patch — appended sections only; existing SEED_USERS/SEED_CATEGORIES/
                   SEED_TIER_LIMITS/products/price-lists sections unchanged)

IMPORT { warehouses, warehouseStock } FROM './schema/warehouses.js'
IMPORT { subscriptionPlans } FROM './schema/billing.js'
IMPORT { upsellRules } FROM './schema/intelligence.js'

SEED_WAREHOUSES = [
    { name: 'Main Warehouse (Mumbai)', location: 'Mumbai, MH', shippingCostWeight: '1.00' },
    { name: 'East Depot (Kolkata)',    location: 'Kolkata, WB', shippingCostWeight: '1.60' },
]

// Laptop stock is deliberately split so neither warehouse alone can cover a
// demo-sized order (assumption 5) — forces the auto-split flow live in the demo.
SEED_STOCK = [
    // productSku, warehouseName, quantityOnHand, reorderThreshold
    { productSku: 'LAPTOP-PRO-14', warehouseName: 'Main Warehouse (Mumbai)', quantityOnHand: 6,  reorderThreshold: 3 },
    { productSku: 'LAPTOP-PRO-14', warehouseName: 'East Depot (Kolkata)',    quantityOnHand: 4,  reorderThreshold: 2 },
    // Setup Service is a SERVICE product type — not stocked (no warehouse_stock row needed).
    // remaining catalog products get generous single-warehouse stock so they never
    // accidentally trigger a demo backorder unless the presenter wants one.
    ...FOR EACH remaining active ONE_TIME product NOT already listed above:
        { productSku: product.sku, warehouseName: 'Main Warehouse (Mumbai)', quantityOnHand: 50, reorderThreshold: 10 }
]

SEED_SUBSCRIPTION_PLANS = [
    { name: 'Cloud Infra — Monthly',   frequency: 'MONTHLY',   price: '12000.00', prorationEnabled: true, cancellationNoticeDays: 7 },
    { name: 'Cloud Infra — Quarterly', frequency: 'QUARTERLY', price: '32000.00', prorationEnabled: true, cancellationNoticeDays: 14 },
]

// Minimal, demonstrable upsell pairing per plan.md §2.6 / A6 — links the Setup Service
// as a promoted cross-sell against the Laptop, so B5's panel has something to show.
SEED_UPSELL_RULES = [
    { triggerProductSku: 'LAPTOP-PRO-14', suggestedProductSku: 'SETUP-SVC-STD', isPromoted: true, minMarginPct: '20.00' },
]

ASYNC FUNCTION seedWarehousesAndStock(db):
    warehouseIdByName = {}
    FOR w IN SEED_WAREHOUSES:
        row = AWAIT db.insert(warehouses).values(w).onConflictDoNothing({ target: warehouses.name }).returning()
        warehouseIdByName[w.name] = row[0]?.id OR (AWAIT db.select().from(warehouses).where(eq(warehouses.name, w.name)))[0].id
        console.log(`[SEED] Warehouse ready: ${w.name}`)

    FOR s IN SEED_STOCK:
        productId = AWAIT resolveProductIdBySku(db, s.productSku)
        warehouseId = warehouseIdByName[s.warehouseName]
        AWAIT db.insert(warehouseStock)
          .values({ warehouseId, productId, quantityOnHand: s.quantityOnHand, reorderThreshold: s.reorderThreshold })
          .onConflictDoUpdate({ target: [warehouseStock.warehouseId, warehouseStock.productId],
                                 set: { quantityOnHand: s.quantityOnHand, reorderThreshold: s.reorderThreshold } })
    console.log(`[SEED] Stock seeded for ${SEED_STOCK.length} warehouse/product pairs`)

ASYNC FUNCTION seedSubscriptionPlans(db):
    FOR p IN SEED_SUBSCRIPTION_PLANS:
        AWAIT db.insert(subscriptionPlans).values(p).onConflictDoNothing({ target: subscriptionPlans.name })
    console.log(`[SEED] ${SEED_SUBSCRIPTION_PLANS.length} subscription plans ready`)

ASYNC FUNCTION seedUpsellRules(db):
    FOR r IN SEED_UPSELL_RULES:
        triggerId = AWAIT resolveProductIdBySku(db, r.triggerProductSku)
        suggestedId = AWAIT resolveProductIdBySku(db, r.suggestedProductSku)
        AWAIT db.insert(upsellRules)
          .values({ triggerProductId: triggerId, suggestedProductId: suggestedId,
                     isPromoted: r.isPromoted, minMarginPct: r.minMarginPct })
          .onConflictDoNothing()
    console.log(`[SEED] ${SEED_UPSELL_RULES.length} upsell rules ready`)

// appended to the existing top-level seed() orchestration, after price-list seeding:
ASYNC FUNCTION seed():
    ...existing users/categories/products/price-lists/governance seeding, unchanged...
    AWAIT seedWarehousesAndStock(db)
    AWAIT seedSubscriptionPlans(db)
    AWAIT seedUpsellRules(db)
    console.log('[SEED] Phase 5–8 master data complete — demo scenario preconditions satisfied')
```

*(`upsellRules`' exact column names — `triggerProductId`/`suggestedProductId`/`isPromoted`/`minMarginPct` — follow Phase 4's `intelligence.js` schema/recommendation-engine naming as established in that phase; not re-derived here.)*

### 4.5 Critical-flow smoke test (`scripts/test-critical-flow.js`, new)

Walks `plan.md` §9.1's ten named tests, in order, across a single coherent demo scenario — using the same `assert`/`request` conventions as the existing `scripts/test-e2e-deep.js`.

```
MODULE scripts.test-critical-flow
IMPORT 'dotenv/config'
IMPORT { createServer } FROM 'node:http'
IMPORT app FROM '../app.js'
IMPORT { connectDatabase } FROM '../config/database.js'

passed = 0; failed = 0
FUNCTION assert(condition, message):
    IF condition: passed++; console.log(`  ✅ ${message}`)
    ELSE: failed++; console.error(`  ❌ ${message}`)

ASYNC FUNCTION run():
    AWAIT connectDatabase()
    server = createServer(app); AWAIT listen(server, 0)
    BASE_URL = `http://127.0.0.1:${server.address().port}/api/v1`
    request = buildRequestHelper(BASE_URL)   // identical shape to test-e2e-deep.js's helper

    TRY:
        // --- Test 1: Login ---
        repLogin = AWAIT request('/auth/login', { method:'POST', body:{ email:'rep@dealflow.io', password: DEMO_PASSWORD } })
        assert(repLogin.status == 200, 'Test 1 — Sales Rep logs in')
        repToken = repLogin.data.data.accessToken
        auth = (token) => ({ Authorization: `Bearer ${token}` })

        managerLogin = AWAIT request('/auth/login', { method:'POST', body:{ email:'manager@dealflow.io', password: DEMO_PASSWORD } })
        managerToken = managerLogin.data.data.accessToken

        financeLogin = AWAIT request('/auth/login', { method:'POST', body:{ email:'finance@dealflow.io', password: DEMO_PASSWORD } })
        financeToken = financeLogin.data.data.accessToken

        // --- Test 2: Configuration already asserted present via seed (Phase 9 §4.4) ---
        tierLimits = AWAIT request('/governance/tier-discount-limits', { headers: auth(repToken) })
        warehousesRes = AWAIT request('/warehouses', { headers: auth(repToken) })
        plansRes = AWAIT request('/subscriptions/plans', { headers: auth(repToken) })   // Phase 6 read endpoint
        assert(tierLimits.data.data.length > 0, 'Test 2 — discount tiers configured')
        assert(warehousesRes.data.data.length >= 2, 'Test 2 — at least two warehouses configured')
        assert(plansRes.data.data.length > 0, 'Test 2 — a subscription plan is configured')

        goldCustomer = AWAIT findSeededGoldCustomer(request, repToken)
        laptop = AWAIT findSeededProduct(request, repToken, 'LAPTOP-PRO-14')
        setupService = AWAIT findSeededProduct(request, repToken, 'SETUP-SVC-STD')

        // --- Test 3: Quote + excessive discount ---
        createRes = AWAIT request('/quotations', { method:'POST', headers: auth(repToken),
            body: { customerId: goldCustomer.id } })
        quotationId = createRes.data.data.id
        AWAIT request(`/quotations/${quotationId}/items`, { method:'POST', headers: auth(repToken),
            body: { productId: laptop.id, quantity: 3, discountPct: 12 } })          // within Hardware ceiling
        AWAIT request(`/quotations/${quotationId}/items`, { method:'POST', headers: auth(repToken),
            body: { productId: setupService.id, quantity: 1, discountPct: 18 } })    // over Service ceiling (plan.md's own example)

        submitRes = AWAIT request(`/quotations/${quotationId}/submit`, { method:'POST', headers: auth(repToken) })
        assert(submitRes.status == 200, 'Test 3 — quotation submitted')
        assert(submitRes.data.data.status == 'PENDING_APPROVAL', 'Test 3 — over-limit service discount auto-routes to approval')
        assert(submitRes.data.data.requiredApprovalLevel IN ('MANAGER','MANAGER_FINANCE'), 'Test 3 — required approval level set')

        // --- Test 4: Upsell ---
        recsRes = AWAIT request(`/quotations/${quotationId}/recommendations`, { headers: auth(repToken) })
        totalsBefore = AWAIT request(`/quotations/${quotationId}`, { headers: auth(repToken) })
        firstRec = recsRes.data.data[0]
        addRecRes = AWAIT request(`/quotations/${quotationId}/recommendations/${firstRec.productId}/add`, { method:'POST', headers: auth(repToken) })
        totalsAfter = AWAIT request(`/quotations/${quotationId}`, { headers: auth(repToken) })
        assert(addRecRes.status == 200, 'Test 4 — upsell recommendation accepted')
        assert(totalsAfter.data.data.grandTotal != totalsBefore.data.data.grandTotal, 'Test 4 — quote total updates live')
        assert(totalsAfter.data.data.estimatedMarginPct != totalsBefore.data.data.estimatedMarginPct, 'Test 4 — margin updates live')

        // --- Test 5: Approval + audit trail ---
        pendingApprovals = AWAIT request('/approvals?status=PENDING', { headers: auth(managerToken) })
        approvalId = pendingApprovals.data.data.find(a => a.quotationId == quotationId).id
        approveRes = AWAIT request(`/approvals/${approvalId}/approve`, { method:'POST', headers: auth(managerToken),
            body: { reason: 'Strategic account — approved with note' } })
        assert(approveRes.status == 200, 'Test 5 — manager approves')
        auditRes = AWAIT request(`/quotations/${quotationId}/approvals`, { headers: auth(managerToken) })
        assert(auditRes.data.data.some(a => a.action == 'APPROVED'), 'Test 5 — audit trail entry created')
        // if blended risk required MANAGER_FINANCE, repeat the approve call as financeToken here

        // --- Test 6: Warehouse split ---
        orderRes = AWAIT request(`/quotations/${quotationId}/orders`, { method:'POST', headers: auth(repToken) })
        orderId = orderRes.data.data.order.id
        allocationRes = AWAIT request(`/orders/${orderId}/allocation`, { headers: auth(repToken) })
        distinctWarehouses = new Set(allocationRes.data.data.allocations.map(a => a.warehouseId))
        assert(distinctWarehouses.size >= 2, 'Test 6 — Laptop line auto-split across two warehouses')

        // --- Test 7: Hybrid billing ---
        billingRes = AWAIT request(`/orders/${orderId}/billing`, { headers: auth(repToken) })
        assert(billingRes.data.data.oneTimeInvoice != null, 'Test 7 — one-time invoice generated')
        assert(billingRes.data.data.billingSchedule.length > 0, 'Test 7 — recurring billing schedule generated')

        // --- Test 8: Negotiation ---
        portalTokenRes = AWAIT request(`/quotations/${quotationId}/portal-token`, { method:'POST', headers: auth(repToken) })
        portalToken = portalTokenRes.data.data.token
        counterRes = AWAIT request(`/portal/quotes/${portalToken}/negotiate`, { method:'POST',
            body: { requestType: 'COUNTER_DISCOUNT', requestedDiscountPct: 25, message: 'Can we do better on the service line?' } })
        assert(counterRes.status == 200, 'Test 8 — customer counter-offer submitted')
        quoteAfterCounter = AWAIT request(`/quotations/${quotationId}`, { headers: auth(repToken) })
        assert(quoteAfterCounter.data.data.status == 'PENDING_APPROVAL', 'Test 8 — counter-offer re-triggers risk → approval')
        AWAIT request(`/approvals/${latestApprovalIdFor(quotationId, managerToken)}/approve`, { method:'POST', headers: auth(managerToken) })

        // --- Test 9: Confirmation ---
        confirmRes = AWAIT request(`/portal/quotes/${portalToken}/confirm`, { method:'POST' })
        assert(confirmRes.status == 200, 'Test 9 — customer confirms quotation')
        orderAfterConfirm = AWAIT request(`/orders/${orderId}`, { headers: auth(repToken) })
        assert(orderAfterConfirm.data.data.status IN ('PENDING_FULFILLMENT','PARTIALLY_FULFILLED','FULFILLED'), 'Test 9 — order proceeds to fulfillment')

        // --- Test 10: Dashboard ---
        healthRes = AWAIT request('/dashboard/health', { headers: auth(managerToken) })
        anomaliesRes = AWAIT request('/dashboard/anomalies', { headers: auth(managerToken) })
        assert(healthRes.status == 200, 'Test 10 — dashboard health summary loads')
        assert(anomaliesRes.status == 200, 'Test 10 — anomaly/alert feed loads')

    CATCH err:
        console.error('[CRITICAL_FLOW_TEST] Unhandled error:', err)
        failed++
    FINALLY:
        AWAIT close(server)
        console.log(`\n${passed} passed, ${failed} failed`)
        process.exit(failed > 0 ? 1 : 0)

run()
```
