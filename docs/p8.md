# DealFlow360 — Phase 8 API Design
## Deal Health + Anomaly Dashboard + Reporting (`plan.md` §8, Hour 7–7.5)

Builds on Phase 1 (auth/RBAC/response envelope), Phase 2 (`governance`, `categories`/`products`), Phase 3 (`quotations` — `lastActivityAt`, `estimatedMarginPct`, `blendedRiskScore`, `requiredApprovalLevel`), Phase 4 (`approval_requests`), Phase 5 (`orders`, `backorders`), Phase 6 (billing — read-only for `orderValue`), and Phase 7 (portal/negotiation — a customer counter-offer bumps `quotations.lastActivityAt`, which is what keeps a deal off the stalled list). Scope is strictly `plan.md` §8.1–8.6: Deal Health cards, Stalled Deals, Discount Anomaly, Delivery Promise Slippage, Automated Nudge, and Reporting. This is the **management layer** — a read-mostly module. It never mutates `quotations`, `orders`, or any earlier-phase table; its only writes are to `deal_alerts` (which it owns) and `audit_logs` (append-only, shared).

---

## 1. Assumptions carried into this phase

1. **`deal_alerts` is a materialized, re-computed cache, not a source of truth.** The four conditions in §8.2–8.4 (stalled, discount anomaly, delivery slippage, low margin) are all *derivable* on demand from `quotations`, `orders`, and `backorders` — nothing new needs to be captured at write time in earlier phases. Rather than adding a cron job (explicitly out of scope per §8.5 bonus note: *"Do NOT sacrifice core workflow for queues/cron"*), this phase runs a **synchronous detection pass** (`refreshDealAlerts()`) at the top of every `GET /dashboard/health` and `GET /dashboard/anomalies` call, before reading. This keeps `deal_alerts` fresh without any background infrastructure, at the cost of a few extra read queries per dashboard load — acceptable at hackathon/demo scale, and exactly the kind of "read that also writes its own cache" pattern the schema's `resolvedBy`/`resolvedAt`/`status` columns on `deal_alerts` were clearly designed for (an ephemeral computed value would have no use for a resolution audit trail).
2. **One open alert per `(quotationId, alertType)`.** `deal_alerts` has no unique constraint enforcing this, so the refresh pass does an explicit `SELECT` for an existing `status='OPEN'` row of that `(quotationId, alertType)` before deciding to insert vs. update-in-place, all inside one transaction guarded by a Postgres advisory lock (`pg_advisory_xact_lock`, keyed to a fixed constant) so concurrent dashboard loads from two managers never race into duplicate rows. This is called out explicitly because it is the one place this phase's design compensates for a schema gap rather than assuming one; no migration is proposed since the advisory-lock serialization is sufficient at this scale.
3. **A condition that stops being true auto-resolves its alert.** If `refreshDealAlerts()` finds an `OPEN` alert of a given type for a quotation but the underlying condition no longer holds (e.g. the rep finally touched a "stalled" quote, or a backorder that was slipping is now on schedule), it sets `status='RESOLVED'`, `resolvedAt=now()`, `resolvedBy=NULL` (system-resolved, distinct from a human clicking "Dismiss"). This keeps the alert feed honest without any manual cleanup step and matches §8.2's dashboard framing ("stalled deals" should disappear the moment they're no longer stalled).
4. **"Stalled" is scoped to quotations still in an active, pre-confirmation lifecycle state.** `plan.md` §8.2 defines it as "quote inactive > N days"; this phase applies that only to `quotations.status IN ('DRAFT','PENDING_APPROVAL','APPROVED','SENT','UNDER_NEGOTIATION')` — a `CONFIRMED`/`COMPLETED`/`CANCELLED`/`REJECTED` quote has left the negotiation loop and inactivity on it is not a deal-health concern. `lastActivityAt` (added to the `quotations` schema in Phase 1, bumped by Phase 3/4/7 mutations) is used directly rather than re-deriving "last touched" from `audit_logs`, since that is precisely the column's documented purpose.
5. **"Discount anomaly" compares a quotation's own effective discount rate against its rep's historical average, computed only from that rep's *settled* prior quotations.** Effective discount rate for one quotation = `discountTotal / NULLIF(subtotal + discountTotal, 0) × 100` (discount as a % of pre-discount value, using `quotations.subtotal`/`discountTotal` directly — no re-read of `quotation_items`). "Historical average" = the mean of that same ratio across the rep's own prior quotations with `status IN ('CONFIRMED','COMPLETED')`, **excluding the quotation currently being evaluated** and excluding reps with fewer than `DEAL_HEALTH_ANOMALY_MIN_SAMPLE` (default `3`) settled quotations (too few data points to call anything anomalous — no alert is raised, matching `plan.md`'s own example which assumes an established rep average). The alert fires when `currentDiscountPct − repAverageDiscountPct >= DISCOUNT_ANOMALY_THRESHOLD_PTS` (env-tunable, default `8`, chosen to match `plan.md`'s own worked example of an 11-point gap triggering the alert while a smaller gap would not always). This condition is evaluated only for quotations still open (same status set as assumption 4) so a rep's own high-discount deal doesn't get flagged again after it settles.
6. **"Low Margin" (the 6th dashboard card, present in `plan.md` §8.1's card list but never separately detailed in §8.2–8.4) reuses `quotations.estimatedMarginPct`**, already computed and persisted by Phase 3's quotation engine on every save. The threshold is `LOW_MARGIN_THRESHOLD_PCT` (env-tunable, default `10`), applied to the same open-status set as assumption 4. No new margin calculation is introduced here; this phase only reads the column and raises `LOW_MARGIN` alerts.
7. **"Delivery Promise Slippage" (§8.4) compares `orders.promisedDeliveryDate` against `orders.estimatedDeliveryDate`**, both populated by Phase 5 at order-creation time. The condition is `estimatedDeliveryDate > promisedDeliveryDate` (the fulfillment engine now expects to deliver later than what was promised), evaluated only for orders with `status IN ('PENDING_FULFILLMENT','PARTIALLY_FULFILLED','BACKORDERED')` — a `FULFILLED` or `CANCELLED` order can no longer slip. This alert is keyed to `orderId` (not `quotationId`) since `deal_alerts.orderId` exists precisely for this case; "Backorders" (the dashboard's 6th metric alongside Low Margin) is a **separate, simpler count** — `COUNT(backorders WHERE status IN ('OPEN','PARTIALLY_FULFILLED'))` — read directly, with no corresponding `deal_alerts` row, since a backorder's own `status` field already *is* its lifecycle tracker (Phase 5) and duplicating it into an alert would be redundant per assumption 1's "don't capture what's already derivable" principle.
8. **"At-Risk Deals" (the dashboard card in §8.1 with no dedicated detection rule of its own) is defined as the distinct count of quotations carrying at least one `OPEN` `deal_alerts` row of *any* type**, after the refresh pass — a deliberately unifying definition so the single `deal_alerts` table doubles as both the anomaly feed and the "at risk" rollup, rather than inventing a fifth, independent risk rule.
9. **Nudge / Escalate / Acknowledge / Dismiss are folded into one endpoint, `POST /dashboard/alerts/:id/actions`**, distinguished by an `action` enum in the body, rather than four separate routes. `plan.md` §8.2's three named actions ("View Deal", "Nudge Rep", "Escalate") and §8.5's "Automated Nudge" are all *notification-shaped* — they change nothing about the underlying quotation/order — so they are modeled uniformly as an `audit_logs` write (`action='DEAL_ALERT_NUDGED'` / `'DEAL_ALERT_ESCALATED'`) plus, for `ACKNOWLEDGE`/`DISMISS` only, a `deal_alerts.status` transition. "View Deal" needs no endpoint at all — the alert payload already carries `quotationId`/`orderId`, and the frontend routes straight to the existing Phase 3/5 detail screens.
10. **`plan.md` §8.5's bonus note ("use a background job later if time permits") is explicitly not built.** Nudge is a synchronous, in-request audit-log write — no notification service, no email/SMS/WhatsApp integration (that is item 4 on `plan.md`'s own Post-MVP list). This keeps the action idempotent-by-audit-trail (each click is its own logged event) rather than requiring outbox/retry infrastructure.
11. **Reporting (§8.6) is one parameterized read endpoint plus one CSV-export variant of the same query, not a metric-per-endpoint API.** `plan.md`'s filter list (Period / Sales Team-Rep / Approval Status / Product-Category) is implemented as a single shared filter-resolution function (`resolveReportFilters(query, actor)`) reused by both `GET /reports` (JSON) and `GET /reports/export` (CSV), so the two can never drift out of sync on what "the same report" means. **"Approval Status" filters on `quotations.status ∈ {PENDING_APPROVAL, APPROVED, REJECTED}`** (not `approval_requests.status`) because that is the vocabulary `plan.md` §8.6 itself uses ("pending, approved, or rejected quotations") and it is a single indexed column already on the aggregate root, avoiding a join for the common case; a quotation with a `MANAGER_FINANCE` chain still shows as `APPROVED`/`PENDING_APPROVAL` at the quotation level regardless of which internal step it's on, which matches how a manager reading a report thinks about it.
12. **`orderValue` in the report is `SUM(orders.grandTotal)` for orders whose parent quotation matches the filters, not quotation `grandTotal`.** A `DRAFT`/`REJECTED` quotation never produced an order, so summing quotation totals would overstate realized revenue; joining through to `orders` (1:1 with a confirmed quotation, per Phase 5's schema) reports only value that actually became a real order. `discountAverage` remains computed at the **quotation** level (`AVG(discountTotal / NULLIF(subtotal+discountTotal,0))` across the filtered set) since discount governance is a quotation-time concept, independent of whether the deal has since become an order.
13. **PDF/XLS export is intentionally not built**, per `plan.md` §8.6's own instruction ("do not sacrifice the business flow to build a complex exporter... CSV first, XLS/PDF only after core workflow is stable"). `GET /reports/export` streams CSV only; a follow-up phase can add format-conversion without touching this phase's query logic.
14. **Role scoping mirrors Phase 3's quotation-visibility convention, applied identically across every endpoint in this phase:** `SALES_REP` sees dashboard cards, alerts, and reports **scoped to `quotations.salesRepId == req.auth.userId`** only (a rep's own pipeline health); `SALES_MANAGER`, `FINANCE`, `OPERATIONS`, `ADMIN` see the **unscoped, org-wide** view, consistent with the Problem Statement's role table ("Sales Manager ... Monitors deal health dashboard", "Finance/Operations ... reconciles... manages fulfillment") and with `plan.md`'s own framing of this phase as "the management layer." A `SALES_REP`-supplied `salesRepId` filter on `/reports` is silently overridden to their own id rather than rejected, so the same query string works for both a rep's personal view and a manager's team view. Alert **actions** (`nudge`/`escalate`/`acknowledge`/`dismiss`) are restricted to `SALES_MANAGER`, `FINANCE`, `OPERATIONS`, `ADMIN` only — a rep does not nudge themselves, matching the Problem Statement's "Sales Manager... Monitors... dashboard" ownership of this workflow.

### 4.1 `GET /dashboard/health` — summary cards

- **Purpose:** the six top-of-dashboard metrics in one call.
- **Auth:** any authenticated internal role. `SALES_REP` → scoped to own quotations/orders. Others → org-wide.
- **Validation:** none (no query params beyond auth).
- **Idempotency:** naturally idempotent (read + cache-refresh, no user-supplied mutation).
- **Transaction boundary:** `refreshDealAlerts(scope)` runs in its own single transaction (advisory-locked); the six count queries that follow are plain reads outside that transaction (no read-your-writes risk since they run after commit).
- **DB operations:**
  1. `refreshDealAlerts(scope)` (see §4.6).
  2. Six aggregate queries, batched via `Promise.all` (no N+1):
     - `activeDeals` = `COUNT(quotations WHERE status IN (open-set) [AND salesRepId=scope])`
     - `pendingApprovals` = `COUNT(quotations WHERE status='PENDING_APPROVAL' [AND salesRepId=scope])`
     - `stalledDeals` = `COUNT(DISTINCT deal_alerts.quotationId WHERE alertType='STALLED' AND status='OPEN' [joined to quotations for scope])`
     - `atRiskDeals` = `COUNT(DISTINCT deal_alerts.quotationId WHERE status='OPEN' [scope])` (assumption 8)
     - `lowMarginDeals` = `COUNT(DISTINCT deal_alerts.quotationId WHERE alertType='LOW_MARGIN' AND status='OPEN' [scope])`
     - `backorders` = `COUNT(backorders WHERE status IN ('OPEN','PARTIALLY_FULFILLED') [joined orderItems→orders→quotations for scope])`
- **Concurrency:** read-only after the advisory-locked refresh; no additional locking needed.
- **Rollback:** only the refresh transaction can fail/rollback; the read queries are non-transactional and simply re-run on retry.
- **External services:** none.
- **Success response (200):**
  ```json
  { "success": true, "data": {
      "activeDeals": 14, "pendingApprovals": 3, "stalledDeals": 2,
      "atRiskDeals": 4, "lowMarginDeals": 1, "backorders": 2
  }}
  ```
- **Errors:** `401` unauthenticated.
- **Performance:** 6 count queries + refresh pass, all indexed (`quotations_status_idx`, `quotations_sales_rep_id_idx`, `deal_alerts_status_idx`, `deal_alerts_type_idx`, `backorders_status_idx`); trivial at hackathon data volumes, and each count query is independently cheap enough that batching via `Promise.all` (rather than one giant `UNION ALL`) keeps the code readable without a real cost.

### 4.2 `GET /dashboard/anomalies` — alert feed

- **Purpose:** the drill-down list behind each card in §4.1 — "Acme Corp, ₹1,20,000, Inactive for 6 days" style rows.
- **Auth:** same as §4.1.
- **Query params:** `alertType` (`STALLED`|`DISCOUNT_ANOMALY`|`DELIVERY_SLIPPAGE`|`LOW_MARGIN`, optional — omitted returns all four), `severity` (`LOW`|`MEDIUM`|`HIGH`, optional), `status` (default `OPEN`; accepts `ACKNOWLEDGED`/`RESOLVED`/`DISMISSED` for a history view), `page`, `limit` (via `parseListQuery`).
- **Validation:** each filter, if present, must be a member of its enum; `400 VALIDATION_FAILED` otherwise.
- **Idempotency:** read-only (after its own `refreshDealAlerts` pass, same as §4.1).
- **Transaction boundary:** identical split to §4.1 — refresh in its own tx, then a single paginated `SELECT`.
- **DB operations:**
  1. `refreshDealAlerts(scope)`.
  2. One paginated query joining `deal_alerts` → `quotations` (for `quoteNumber`, `customerName` via `customers`, `salesRepId`/name via `users`, `grandTotal`) and, where `orderId IS NOT NULL`, → `orders` for `orderNumber`/dates — a single query with `LEFT JOIN`s, never N+1 per row.
  3. `COUNT(*)` for `buildMeta` (same filtered `WHERE`, run alongside via `Promise.all`).
- **Concurrency:** none beyond the refresh pass's advisory lock.
- **Rollback:** n/a (read-only).
- **Success response (200):**
  ```json
  { "success": true,
    "data": [
      { "id": "...", "alertType": "STALLED", "severity": "MEDIUM", "status": "OPEN",
        "message": "Inactive for 6 days",
        "quotationId": "...", "quoteNumber": "Q-2026-0042",
        "customerName": "Acme Corp", "grandTotal": "120000.00",
        "salesRepName": "Alex Morgan", "orderId": null, "createdAt": "..." }
    ],
    "meta": { "total": 6, "page": 1, "limit": 20, "totalPages": 1, "hasNextPage": false, "hasPrevPage": false }
  }
  ```
- **Errors:** `400` invalid filter enum value; `401` unauthenticated.
- **Performance:** indexed on `deal_alerts_status_idx`/`deal_alerts_type_idx`; `LIMIT`/`OFFSET` capped at `limit ≤ 100` by `parseListQuery`.

### 4.3 `POST /dashboard/alerts/:id/actions` — nudge / escalate / acknowledge / dismiss

- **Purpose:** the three buttons in §8.2 plus §8.5's automated nudge, unified (assumption 9).
- **Auth:** `SALES_MANAGER`, `FINANCE`, `OPERATIONS`, `ADMIN` only.
- **Request body:** `{ "action": "NUDGE" | "ESCALATE" | "ACKNOWLEDGE" | "DISMISS", "note": "optional string" }`.
- **Validation:** `id` UUID must resolve to an existing `deal_alerts` row; `action` must be one of the four literals; `404 NOT_FOUND` / `400 VALIDATION_FAILED` respectively. Acting on an alert whose `status` is already `RESOLVED`/`DISMISSED` is rejected with `409 CONFLICT` ("alert is no longer open") **except** that `NUDGE`/`ESCALATE` are still permitted on an `ACKNOWLEDGED` alert (a manager can still nudge after acknowledging), only a terminal `RESOLVED`/`DISMISSED` state blocks further action.
- **Idempotency:** **not** treated as idempotent by dedup — each `NUDGE`/`ESCALATE` call is a deliberate, individually logged event (assumption 10), so repeated identical calls create repeated audit rows by design (this mirrors a human clicking "Nudge" twice meaning two nudges). `ACKNOWLEDGE`/`DISMISS` **are** idempotent in effect: calling either again on an already-`ACKNOWLEDGED`/`DISMISSED` alert of the same target status is a no-op `200`, not an error (only a transition to/from `RESOLVED` — which the system alone sets — is blocked as above).
- **Transaction boundary:** single transaction: `SELECT ... FOR UPDATE` the `deal_alerts` row → (for `ACKNOWLEDGE`/`DISMISS` only) `UPDATE deal_alerts SET status=..., resolvedBy=actorId, resolvedAt=now()` → `INSERT audit_logs`.
- **DB operations:**
  1. `SELECT deal_alerts WHERE id=:id FOR UPDATE`.
  2. Branch on `action`:
     - `NUDGE` / `ESCALATE`: no `deal_alerts` write; only the audit log captures it (`action='DEAL_ALERT_NUDGED'`/`'DEAL_ALERT_ESCALATED'`, `newValue={alertId, quotationId, note}`).
     - `ACKNOWLEDGE`: `UPDATE deal_alerts SET status='ACKNOWLEDGED'` (no `resolvedAt` — acknowledgement isn't resolution).
     - `DISMISS`: `UPDATE deal_alerts SET status='DISMISSED', resolvedBy=actorId, resolvedAt=now()`.
  3. `audit.service.recordAuditTrail({ actorId, entityType:'deal_alert', entityId:id, action:'DEAL_ALERT_'+action, reason:note, oldValue:{status:before}, newValue:{status:after} }, tx)`.
- **Concurrency:** the row lock (`FOR UPDATE`) serializes two managers acting on the same alert simultaneously; the second sees the post-update `status` and, if it now conflicts with their requested action (e.g. someone else already dismissed it), gets the `409` above.
- **Rollback:** any failure (including the audit insert, per Phase 2's established "audit failure rolls back the whole mutation" pattern) rolls back the `deal_alerts` update — an action is never silently unaudited.
- **External services:** none (assumption 10 — no notification dispatch).
- **Success response (200):** the updated alert row (or unchanged row for `NUDGE`/`ESCALATE`), plus `data.auditLogId`.
- **Error responses:** `400` invalid `action`; `401` unauthenticated; `403` wrong role; `404` alert not found; `409` alert already `RESOLVED`/terminal for the requested transition.
- **Performance:** single-row lock, single-row update, single insert — O(1).

### 4.4 `GET /reports` — aggregated metrics

- **Purpose:** the filterable reporting surface behind §8.6.
- **Auth:** any authenticated internal role. `SALES_REP` → `salesRepId` filter forced to self (assumption 14); others → free choice or unfiltered.
- **Query params:** `period` (`today`|`week`|`month`|`custom`, default `month`), `from`/`to` (ISO dates, required only when `period=custom`), `salesRepId` (UUID, optional), `approvalStatus` (`PENDING_APPROVAL`|`APPROVED`|`REJECTED`, optional), `productId` (UUID, optional), `categoryId` (UUID, optional — mutually exclusive with `productId`; if both given, `productId` wins and `categoryId` is ignored, documented in the validator's error-free "last one wins" note rather than rejected, since combining them is a harmless redundancy not a contradiction).
- **Validation:** date range sanity (`from ≤ to`, both required together when `period=custom`); each enum/UUID checked; `400 VALIDATION_FAILED` with field-level `details` on any failure.
- **Idempotency:** read-only, naturally idempotent.
- **Transaction boundary:** none required — all reads are independent `SELECT`s at default (read-committed) isolation; a report is a point-in-time snapshot by nature, not a value that needs cross-query consistency guarantees stronger than what a single fast round of queries already gives.
- **DB operations (all batched via `Promise.all`, zero N+1):**
  1. `resolveReportFilters(query, actor)` → `{ dateFrom, dateTo, salesRepId, approvalStatus, productId, categoryId }` (pure function, no DB).
  2. **Metrics:**
     - `quotationCount` = `COUNT(quotations WHERE createdAt BETWEEN dateFrom AND dateTo [AND filters])`
     - `approvalCount` = same `WHERE` + `status='APPROVED'`
     - `rejectedCount` = same `WHERE` + `status='REJECTED'`
     - `discountAverage` = `AVG(discountTotal / NULLIF(subtotal+discountTotal,0)) × 100` over the filtered quotation set (assumption 12)
     - `orderValue` = `SUM(orders.grandTotal)` joined `orders.quotationId = quotations.id`, same filtered quotation set (assumption 12)
  3. **`topProducts`** (top 8 by `SUM(quotation_items.lineTotal)`): `quotation_items` joined to `quotations` (filtered set) and `products`, `GROUP BY productId`, ordered `DESC`, includes `unitsSold=SUM(quantity)`, `timesDiscounted=COUNT(*) WHERE discountPct>0`.
  4. **`salesByRep`** (only when no `salesRepId` filter is applied — a single-rep report has nothing to break down further): `quotations` filtered set `GROUP BY salesRepId`, joined `users` for name, returns `quotationCount`, `orderValue` (joined `orders`), `discountAverage` per rep.
- **Concurrency:** none — pure reads.
- **Rollback:** n/a.
- **External services:** none.
- **Success response (200):**
  ```json
  { "success": true, "data": {
      "filters": { "period":"month","from":"2026-08-01","to":"2026-08-31","salesRepId":null,"approvalStatus":null,"productId":null,"categoryId":null },
      "metrics": { "quotationCount": 42, "approvalCount": 30, "rejectedCount": 4, "discountAverage": 9.4, "orderValue": "2450000.00" },
      "topProducts": [ { "productId":"...", "name":"Laptop Pro 14", "unitsSold": 18, "revenue":"1440000.00", "timesDiscounted": 11 } ],
      "salesByRep": [ { "salesRepId":"...", "name":"Alex Morgan", "quotationCount": 14, "orderValue":"820000.00", "discountAverage": 8.1 } ]
  }}
  ```
- **Errors:** `400` invalid filters/date range; `401` unauthenticated.
- **Performance:** indexed on `quotations_status_idx`, `quotations_sales_rep_id_idx`, `quotation_items_product_id_idx`; `topProducts`/`salesByRep` are capped, single `GROUP BY` queries, not per-product/per-rep loops.

### 4.5 `GET /reports/export` — CSV export

- **Purpose:** §8.6's "Export options: PDF/XLS" scoped down to CSV-only (assumption 13).
- **Auth/validation/filters:** identical to §4.4 — calls the same `resolveReportFilters`.
- **Idempotency:** read-only.
- **DB operations:** one streaming query — the same filtered `quotations` set as §4.4's metrics query, but row-level (`quoteNumber`, `customerName`, `salesRepName`, `status`, `subtotal`, `discountTotal`, `taxTotal`, `grandTotal`, `createdAt`), ordered by `createdAt DESC`, read via a DB cursor/streaming query rather than loading the full result set into memory (guards against an unbounded export on a large date range).
- **Success response (200):** `Content-Type: text/csv`, `Content-Disposition: attachment; filename="dealflow360-report-<from>-<to>.csv"`, body streamed row-by-row.
- **Errors:** same as §4.4, returned as JSON (checked **before** streaming starts, so a validation failure never produces a partially-written CSV).
- **Performance:** streaming avoids buffering the whole export in memory; acceptable row-count for a hackathon dataset either way, but the pattern is the correct one to not have to revisit later.

### 4.6 `refreshDealAlerts(scope)` — internal detection pass (no HTTP route)

Called by §4.1 and §4.2 only; not directly reachable. `scope` is `{ salesRepId }` or `null` (org-wide), from assumption 14.

```
BEGIN TRANSACTION
  PG_ADVISORY_XACT_LOCK(hashtext('deal_alerts_refresh'))   -- serializes concurrent refreshes (assumption 2)

  candidates = []

  -- STALLED (assumption 4)
  openQuotes = SELECT id, salesRepId, lastActivityAt, grandTotal, quoteNumber
               FROM quotations
               WHERE status IN (OPEN_QUOTE_STATUSES)
               [AND salesRepId = scope.salesRepId]
  FOR q IN openQuotes:
    daysInactive = DATEDIFF(NOW(), q.lastActivityAt)
    IF daysInactive > env.STALLED_DEAL_THRESHOLD_DAYS:
      candidates.push({ quotationId: q.id, alertType: 'STALLED', severity: severityForDays(daysInactive),
                         message: `Inactive for ${daysInactive} days` })

  -- DISCOUNT_ANOMALY (assumption 5)
  FOR q IN openQuotes:
    currentPct = effectiveDiscountPct(q)
    repAvg = SELECT AVG(effectiveDiscountPct) FROM quotations
             WHERE salesRepId=q.salesRepId AND status IN ('CONFIRMED','COMPLETED') AND id != q.id
    sampleSize = SELECT COUNT(*) FROM quotations
                 WHERE salesRepId=q.salesRepId AND status IN ('CONFIRMED','COMPLETED') AND id != q.id
    IF sampleSize >= env.DEAL_HEALTH_ANOMALY_MIN_SAMPLE AND (currentPct - repAvg) >= env.DISCOUNT_ANOMALY_THRESHOLD_PTS:
      candidates.push({ quotationId: q.id, alertType: 'DISCOUNT_ANOMALY', severity: 'HIGH',
                         message: `${(currentPct-repAvg).toFixed(1)} points above rep's historical average` })

  -- LOW_MARGIN (assumption 6)
  FOR q IN openQuotes WHERE estimatedMarginPct IS NOT NULL AND estimatedMarginPct < env.LOW_MARGIN_THRESHOLD_PCT:
      candidates.push({ quotationId: q.id, alertType: 'LOW_MARGIN', severity: 'MEDIUM',
                         message: `Estimated margin ${q.estimatedMarginPct}%` })

  -- DELIVERY_SLIPPAGE (assumption 7)
  openOrders = SELECT id, quotationId, promisedDeliveryDate, estimatedDeliveryDate
               FROM orders JOIN quotations ON orders.quotationId = quotations.id
               WHERE orders.status IN ('PENDING_FULFILLMENT','PARTIALLY_FULFILLED','BACKORDERED')
               [AND quotations.salesRepId = scope.salesRepId]
  FOR o IN openOrders WHERE o.promisedDeliveryDate IS NOT NULL AND o.estimatedDeliveryDate IS NOT NULL
                         AND o.estimatedDeliveryDate > o.promisedDeliveryDate:
      candidates.push({ quotationId: o.quotationId, orderId: o.id, alertType: 'DELIVERY_SLIPPAGE', severity: 'HIGH',
                         message: `Estimated delivery ${o.estimatedDeliveryDate} is after the promised ${o.promisedDeliveryDate}` })

  -- Upsert candidates (assumption 2/3)
  activeKeys = Set()
  FOR c IN candidates:
    activeKeys.add(`${c.quotationId}:${c.alertType}`)
    existing = SELECT * FROM deal_alerts WHERE quotationId=c.quotationId AND alertType=c.alertType AND status='OPEN'
    IF existing:
      UPDATE deal_alerts SET message=c.message, severity=c.severity WHERE id=existing.id
    ELSE:
      INSERT INTO deal_alerts (quotationId, orderId, alertType, severity, message, status) VALUES (..., 'OPEN')

  -- Auto-resolve conditions no longer true (assumption 3)
  staleOpenAlerts = SELECT * FROM deal_alerts
                    WHERE status='OPEN' [AND quotationId IN (scope-visible quotation ids)]
  FOR a IN staleOpenAlerts:
    IF `${a.quotationId}:${a.alertType}` NOT IN activeKeys:
      UPDATE deal_alerts SET status='RESOLVED', resolvedAt=NOW(), resolvedBy=NULL WHERE id=a.id

COMMIT
```

```
MODULE dealHealth.detectors

OPEN_QUOTE_STATUSES = ['DRAFT','PENDING_APPROVAL','APPROVED','SENT','UNDER_NEGOTIATION']
OPEN_ORDER_STATUSES = ['PENDING_FULFILLMENT','PARTIALLY_FULFILLED','BACKORDERED']

FUNCTION effectiveDiscountPct(quotation):
    preDiscountValue = quotation.subtotal + quotation.discountTotal
    IF preDiscountValue <= 0: RETURN 0
    RETURN (quotation.discountTotal / preDiscountValue) * 100

FUNCTION daysSince(timestamp):
    RETURN FLOOR((NOW() - timestamp) IN days)

FUNCTION severityForStaleDays(days, thresholdDays):
    IF days >= thresholdDays * 3: RETURN 'HIGH'
    IF days >= thresholdDays * 1.5: RETURN 'MEDIUM'
    RETURN 'LOW'

FUNCTION isStalled(quotation, thresholdDays):
    RETURN OPEN_QUOTE_STATUSES.includes(quotation.status)
           AND daysSince(quotation.lastActivityAt) > thresholdDays

FUNCTION isLowMargin(quotation, thresholdPct):
    RETURN OPEN_QUOTE_STATUSES.includes(quotation.status)
           AND quotation.estimatedMarginPct != null
           AND quotation.estimatedMarginPct < thresholdPct

FUNCTION isDiscountAnomaly(currentPct, repAveragePct, sampleSize, minSample, thresholdPts):
    IF sampleSize < minSample: RETURN false
    RETURN (currentPct - repAveragePct) >= thresholdPts

FUNCTION isDeliverySlipping(order):
    RETURN OPEN_ORDER_STATUSES.includes(order.status)
           AND order.promisedDeliveryDate != null AND order.estimatedDeliveryDate != null
           AND order.estimatedDeliveryDate > order.promisedDeliveryDate

EXPORT { OPEN_QUOTE_STATUSES, OPEN_ORDER_STATUSES, effectiveDiscountPct, daysSince,
         severityForStaleDays, isStalled, isLowMargin, isDiscountAnomaly, isDeliverySlipping }
```

```
MODULE dealHealth.service
IMPORT { getDb } FROM '../../config/database.js'
IMPORT * as repo FROM './dealHealth.repository.js'
IMPORT * as detect FROM './dealHealth.detectors.js'
IMPORT { recordAuditTrail } FROM '../audit/audit.service.js'

FUNCTION scopeFor(actor):
    IF actor.role == 'SALES_REP': RETURN { salesRepId: actor.id }
    RETURN { salesRepId: null }

// ---- §4.6 detection pass ----
ASYNC FUNCTION refreshDealAlerts(scope):
    db = getDb()
    AWAIT db.transaction(ASYNC (tx) => {
        AWAIT repo.acquireRefreshLock(tx)

        openQuotes = AWAIT repo.findOpenQuotations(tx, scope)
        openOrders = AWAIT repo.findOpenOrdersWithDates(tx, scope)

        candidates = []

        FOR q IN openQuotes:
            IF detect.isStalled(q, env.STALLED_DEAL_THRESHOLD_DAYS):
                days = detect.daysSince(q.lastActivityAt)
                candidates.push({ quotationId: q.id, alertType: 'STALLED',
                    severity: detect.severityForStaleDays(days, env.STALLED_DEAL_THRESHOLD_DAYS),
                    message: `Inactive for ${days} days` })

            IF detect.isLowMargin(q, env.LOW_MARGIN_THRESHOLD_PCT):
                candidates.push({ quotationId: q.id, alertType: 'LOW_MARGIN', severity: 'MEDIUM',
                    message: `Estimated margin ${q.estimatedMarginPct}%` })

            stats = AWAIT repo.findRepDiscountStats(tx, q.salesRepId, q.id)
            currentPct = detect.effectiveDiscountPct(q)
            IF detect.isDiscountAnomaly(currentPct, stats.avgPct OR 0, stats.sampleSize, env.DEAL_HEALTH_ANOMALY_MIN_SAMPLE, env.DISCOUNT_ANOMALY_THRESHOLD_PTS):
                gap = currentPct - stats.avgPct
                candidates.push({ quotationId: q.id, alertType: 'DISCOUNT_ANOMALY', severity: 'HIGH',
                    message: `${gap.toFixed(1)} points above rep's historical average` })

        FOR o IN openOrders:
            IF detect.isDeliverySlipping(o):
                candidates.push({ quotationId: o.quotationId, orderId: o.id, alertType: 'DELIVERY_SLIPPAGE', severity: 'HIGH',
                    message: `Estimated delivery ${o.estimatedDeliveryDate} is after promised ${o.promisedDeliveryDate}` })

        activeKeys = new Set(candidates.map(c => `${c.quotationId}:${c.alertType}`))

        FOR c IN candidates:
            AWAIT repo.upsertAlert(tx, c)

        openAlerts = AWAIT repo.findOpenAlertsInScope(tx, scope)
        FOR a IN openAlerts:
            IF NOT activeKeys.has(`${a.quotationId}:${a.alertType}`):
                AWAIT repo.resolveAlert(tx, a.id)
    })

// ---- §4.1 ----
ASYNC FUNCTION getHealthSummary(actor):
    scope = scopeFor(actor)
    AWAIT refreshDealAlerts(scope)
    db = getDb()

    [activeDeals, pendingApprovals, stalledDeals, atRiskDeals, lowMarginDeals, backorders] = AWAIT Promise.all([
        repo.countActiveDeals(db, scope),
        repo.countPendingApprovals(db, scope),
        repo.countDistinctAlertQuotations(db, scope, 'STALLED'),
        repo.countDistinctAlertQuotations(db, scope, null),
        repo.countDistinctAlertQuotations(db, scope, 'LOW_MARGIN'),
        repo.countOpenBackorders(db, scope),
    ])

    RETURN { activeDeals, pendingApprovals, stalledDeals, atRiskDeals, lowMarginDeals, backorders }

// ---- §4.2 ----
ASYNC FUNCTION getAlerts(actor, filters, listQuery):
    scope = scopeFor(actor)
    AWAIT refreshDealAlerts(scope)
    db = getDb()
    { rows, total } = AWAIT repo.listAlerts(db, scope, filters, listQuery)
    RETURN { rows, total }

// ---- §4.3 ----
ASYNC FUNCTION actOnAlert(actor, alertId, action, note):
    db = getDb()
    RETURN AWAIT db.transaction(ASYNC (tx) => {
        alert = AWAIT repo.findAlertForUpdate(tx, alertId)
        IF NOT alert: THROW NotFoundError('Alert not found')

        IF alert.status IN ('RESOLVED','DISMISSED'):
            THROW ConflictError(`Alert is already ${alert.status.toLowerCase()}`)

        beforeStatus = alert.status
        afterStatus = beforeStatus

        SWITCH action:
            CASE 'NUDGE':
            CASE 'ESCALATE':
                // no state change — logged event only
                BREAK
            CASE 'ACKNOWLEDGE':
                afterStatus = 'ACKNOWLEDGED'
                AWAIT repo.updateAlertStatus(tx, alertId, { status: 'ACKNOWLEDGED', resolvedBy: null, resolvedAt: null })
                BREAK
            CASE 'DISMISS':
                afterStatus = 'DISMISSED'
                AWAIT repo.updateAlertStatus(tx, alertId, { status: 'DISMISSED', resolvedBy: actor.id, resolvedAt: NOW() })
                BREAK

        auditEntry = AWAIT recordAuditTrail({
            actorId: actor.id, entityType: 'deal_alert', entityId: alertId,
            action: `DEAL_ALERT_${action}`, reason: note ?? null,
            oldValue: { status: beforeStatus }, newValue: { status: afterStatus },
        }, tx)

        RETURN { id: alertId, status: afterStatus, auditLogId: auditEntry.id }
    })

EXPORT { refreshDealAlerts, getHealthSummary, getAlerts, actOnAlert }
```

```
MODULE dealHealth.validator
IMPORT { ValidationError } FROM '../../common/errors.js'

ALERT_TYPES = ['STALLED','DISCOUNT_ANOMALY','DELIVERY_SLIPPAGE','LOW_MARGIN']
SEVERITIES = ['LOW','MEDIUM','HIGH']
ALERT_STATUSES = ['OPEN','ACKNOWLEDGED','RESOLVED','DISMISSED']
ACTIONS = ['NUDGE','ESCALATE','ACKNOWLEDGE','DISMISS']

FUNCTION validateAlertFilters(query):
    errors = {}
    IF query.alertType AND NOT ALERT_TYPES.includes(query.alertType): errors.alertType = 'Invalid alertType'
    IF query.severity AND NOT SEVERITIES.includes(query.severity): errors.severity = 'Invalid severity'
    IF query.status AND NOT ALERT_STATUSES.includes(query.status): errors.status = 'Invalid status'
    IF Object.keys(errors).length > 0: THROW ValidationError('Invalid filters', errors)
    RETURN {
        alertType: query.alertType ?? null,
        severity: query.severity ?? null,
        status: query.status ?? 'OPEN',
    }

FUNCTION validateAlertAction(body):
    IF NOT body.action OR NOT ACTIONS.includes(body.action):
        THROW ValidationError('Invalid action', { action: `must be one of ${ACTIONS.join(', ')}` })
    IF body.note != null AND typeof body.note != 'string':
        THROW ValidationError('Invalid note', { note: 'must be a string' })
    RETURN { action: body.action, note: body.note ?? null }

EXPORT { validateAlertFilters, validateAlertAction, ALERT_TYPES, SEVERITIES, ALERT_STATUSES, ACTIONS }
```

```
      .groupBy(quotations.salesRepId)

    orderValueByRep = Map(orderRows.map(r => [r.salesRepId, r.orderValue]))
    RETURN rows.map(r => ({ ...r, orderValue: orderValueByRep.get(r.salesRepId) OR '0' }))

ASYNC FUNCTION* streamExportRows(db, filters):
    quoteConds = baseQuotationConditions(filters)
    cursor = db.select({
        quoteNumber: quotations.quoteNumber, customerName: customers.name, salesRepName: users.name,
        status: quotations.status, subtotal: quotations.subtotal, discountTotal: quotations.discountTotal,
        taxTotal: quotations.taxTotal, grandTotal: quotations.grandTotal, createdAt: quotations.createdAt,
      })
      .from(quotations)
      .leftJoin(customers, eq(quotations.customerId, customers.id))
      .leftJoin(users, eq(quotations.salesRepId, users.id))
      .where(and(...quoteConds))
      .orderBy(desc(quotations.createdAt))
      .cursor()   // driver-level streaming cursor — rows yielded incrementally, not buffered

    FOR AWAIT (row OF cursor): YIELD row

EXPORT { getMetrics, getTopProducts, getSalesByRep, streamExportRows }
```

```
MODULE reporting.validator
IMPORT { ValidationError } FROM '../../common/errors.js'

APPROVAL_STATUSES = ['PENDING_APPROVAL','APPROVED','REJECTED']
PERIODS = ['today','week','month','custom']

FUNCTION periodToRange(period, from, to):
    now = NOW()
    SWITCH period:
        CASE 'today':  RETURN { dateFrom: startOfDay(now), dateTo: endOfDay(now) }
        CASE 'week':   RETURN { dateFrom: startOfWeek(now), dateTo: endOfDay(now) }
        CASE 'month':  RETURN { dateFrom: startOfMonth(now), dateTo: endOfDay(now) }
        CASE 'custom':
            IF NOT from OR NOT to: THROW ValidationError('Custom period requires from and to', { from: 'required', to: 'required' })
            IF new Date(from) > new Date(to): THROW ValidationError('Invalid date range', { from: 'must be <= to' })
            RETURN { dateFrom: from, dateTo: to }

FUNCTION resolveReportFilters(query, actor):
    errors = {}
    period = query.period OR 'month'
    IF NOT PERIODS.includes(period): errors.period = 'Invalid period'
    IF query.approvalStatus AND NOT APPROVAL_STATUSES.includes(query.approvalStatus): errors.approvalStatus = 'Invalid approvalStatus'
    IF query.salesRepId AND NOT isUuid(query.salesRepId): errors.salesRepId = 'Invalid UUID'
    IF query.productId AND NOT isUuid(query.productId): errors.productId = 'Invalid UUID'
    IF query.categoryId AND NOT isUuid(query.categoryId): errors.categoryId = 'Invalid UUID'
    IF Object.keys(errors).length > 0: THROW ValidationError('Invalid report filters', errors)

    { dateFrom, dateTo } = periodToRange(period, query.from, query.to)

    // assumption 14 — a SALES_REP can never see anyone else's numbers
    salesRepId = actor.role == 'SALES_REP' ? actor.id : (query.salesRepId ?? null)

    RETURN {
        period, dateFrom, dateTo, salesRepId,
        approvalStatus: query.approvalStatus ?? null,
        productId: query.productId ?? null,
        // assumption: productId wins over categoryId when both given
        categoryId: query.productId ? null : (query.categoryId ?? null),
    }

EXPORT { resolveReportFilters, APPROVAL_STATUSES, PERIODS }
```

```
exportReportController = asyncHandler(ASYNC (req, res) => {
    // validate filters BEFORE writing any bytes to the response (assumption 13's
    // "never a partially-written CSV on a validation error")
    filters = service.resolveReportFilters(req.query, req.user)   // throws before headers are set on bad input

    filename = `dealflow360-report-${filters.dateFrom}-${filters.dateTo}.csv`
    res.setHeader('Content-Type', 'text/csv')
    res.setHeader('Content-Disposition', `attachment; filename="${filename}"`)

    res.write('Quote Number,Customer,Sales Rep,Status,Subtotal,Discount,Tax,Grand Total,Created At\n')
    FOR AWAIT (row OF service.streamExportRows(req.user, req.query)):
        res.write(csvEscapeRow([row.quoteNumber, row.customerName, row.salesRepName, row.status,
                                 row.subtotal, row.discountTotal, row.taxTotal, row.grandTotal, row.createdAt]) + '\n')
    res.end()
})

FUNCTION csvEscapeRow(fields):
    RETURN fields.map(f => {
        s = String(f ?? '')
        RETURN /[",\n]/.test(s) ? `"${s.replace(/"/g, '""')}"` : s
    }).join(',')

EXPORT { getReportController, exportReportController }
```
